# 任务图：任务之间的关联，与停止的传染

本文描述内核中任务和后台 job 的起因边与停止传播。工作流 DAG 的边传递交付和分支选择，两张图各自维护依赖。模型使用的工作流工具见[会话与工作流](WORKFLOWS.md)。

## 0. 要解决什么

一个任务被停下时，**为它而起的工作要跟着停**，并且要停得对：

- **不多停**：B 手上同时有 A 的任务 P、D 的任务 Q，B 为 Q 派出去的活不能因为撤 P 而被撤。
- **不漏停**：A→B→C→D 一路派下去，C 先交了差，D 还在跑；撤 A 的任务时，D 也要停（上一轮评审的问题 3）。
- **不在停的过程中派出要停的东西**：被 `after` 挡住的任务，不能因为树里另一个任务先被撤而被放行、交给承接者（问题 1）。
- **该知道的人知道，且只知道一次**：撤的人不收回音；可是在等结果的会话如果不是撤的人，就不能被悄悄丢下（问题 2）。

"为谁而起"由中枢推断，不要模型声明。

## 1. 图

**节点是任务**：智能体的任务和后台任务（job）都是。

**根**是会话本身：在会话里没有任何未结束任务时派出的活（用户在会话里直接交代的事），它的父任务集合为空，挂在根上。根不是节点，也不会被撤任务波及。

**两类边**，都从新任务指向已有任务：

| 边 | 含义 | 谁定 | 用途 |
| - | - | - | - |
| 起因边 `parents` | 这件活是为哪些任务而起 | 中枢推断 | 停止传染 |
| 次序边 `after` | 这件活要等哪些任务结束才开始 | 派发者声明 | 放行 |

两类边都只指向**创建时已存在**的任务，所以图天然无环，**创建顺序就是拓扑序**。算法依赖这一点，不需要检测环。

`await_tasks` 的等待（gate）不是边：它属于会话，说的是"这几个结果一起交给我"，与任务为何存在无关。

### 1.1 起因边怎么推断

派发（`dispatch_task`）或启动后台任务（`start_job`）时：

```
parents(新任务) = 派发所在会话里，已交给模型、尚未结束的智能体任务
```

- 只取**本会话**的：每个 Agent 只有一条对话，一次只做一件事，这一轮开着的任务就是"这一轮在为谁干活"。
- 只取**已交给模型**的（`running`）：模型还没看到的任务不可能是它派活的理由。
- 取到几个就记几个。多于一个时，不猜是哪一个，交给 2.2 的判定。

起因边创建时写定，之后不变。

## 2. 算法

全部是图上的纯函数，不碰存储和会话。

### 2.1 支撑者 `holders(n)`

一个活着的任务之所以还该存在，是因为有谁在"撑着"它：

```
holders(n) = 并集，对 n 的每个父任务 p：
               p 未结束      → { p }
               p 已完成      → holders(p)      // 穿过做完了的中间任务
               p 以别的方式结束（取消、失败、中断）→ 空
             parents(n) 为空 → { 根 }
```

穿透是"不漏停"的关键：C 交了差，C 为它派出、还在跑的活就改由 C 的任务的支撑者撑着，一直追到活着的祖先或根。

只有**完成**才穿透。被撤或失败的任务已经不存在了，不再撑着任何东西：它的树在它停下时已经撤过一遍，留下的只是当时还有别人撑着的活（spared）。如果它也穿透，这些活就会被它的上级"撑住"，后来别的父任务被撤时也撤不掉。支撑者因此可能为空：什么都不撑着它了，在撤销时它就跟着撤。

结果按任务记忆，每个任务只算一次。

### 2.2 撤销集 `doom(r)`

撤任务 r 时，哪些任务一起撤：

```
D = { r }
按创建顺序遍历 r 沿起因边可达的后代 n：
    n 未结束，且 holders(n) 全部在 D 里（含为空） →  D 加入 n
    n 未结束，但有支撑者在 D 外                →  记入 spared（不撤，只告知）
返回 D、spared
```

因为是拓扑序，处理 n 时，它的支撑者在不在 D 里已经定了。复杂度与后代数和边数成正比。

例子：

| 情形 | 推演 | 结果 |
| - | - | - |
| P(A→B)，X 为 P 派给 C，Z 为 X 派给 D，X 已交差 | holders(Z) = holders(X) = {P} ⊆ D | Z 被撤 |
| B 同时有 P、Q，c 是在那时派出的 | holders(c) = {P, Q}，Q ∉ D | c 不撤，记入 spared |
| B 会话里没有任务时派出的 e | holders(e) = {根} | 与 P 无关，不在后代里 |
| 接上一行，之后 Q 也被撤 | P 已取消，不再撑着；holders(c) = {Q} ⊆ D | c 被撤 |

### 2.3 放行 `releasable(E)`

一批任务 E 结束时，哪些被 `after` 挡着的任务可以放行：

```
{ t | t 被挡着，t ∉ E，t.after 中每一个都已结束或在 E 里 }
```

撤销时 E = D，**一次算完**：D 里的任务不会被放行（问题 1），D 外等 D 的任务照常放行，拿到的是"已取消"的前置结果（现行规则不变）。

## 4. 业务

### 4.1 一次撤销是一个事务

输入：要撤的任务 r，停止方 X（主体：某个 Agent、用户或中枢，[KERNEL.md](KERNEL.md) 2）。先经 `task.pre_stop` 裁决：Agent 只能撤自己派发的任务，用户可以撤任何任务。

1. **判定**：`(D, spared) = doom(r)`；`cascade.pre_propagate` 可以让 spared 也一起撤。
2. **记录**：r 按停止的原因结束，D 里其余任务记为 `cancelled`（`ended.reason = cascaded`，停止方是 X，`cause` 是 r），结果写明根因："随 r 被 X 撤销"。智能体任务撤回还在队列里的投递；排队中的后台任务直接移除；运行中的后台任务中止调用，结束时按第 4 步当时的决定处理。
3. **停下或告知承接者**：D 里已交给模型的智能体任务，其承接者会话分两种。会话开着的任务全在 D 里、又正在工作的，组成集合 H：它们的工作被停下（`session/cancel`），不再另行告知。其余的（承接者不是 X 的）组成集合 N：每个会话收到**一条**通知（`lazy`：承接者在工作就插进去，空闲就留在收件箱随下一轮附上），列出：它手上被撤的任务、中枢替它撤掉的它派出的活、它派出但因还服务于别的任务而没撤的活（spared）。
4. **告知派发者**：对 D 里每个任务 t，看它的派发会话 F(t)：
   - F(t) 属于 X（自己撤的，不论从它的哪个会话撤），或 F(t) 在 N 里（已在第 3 步的通知里），或在 H 里（它的工作已整体撤掉）→ **静默**：不送结果，从 F(t) 的等待里移除 t；等待因此为空就关掉，因此满足就送出其余结果。
   - 否则 → 照常送回 `cancelled` 结果，走它的等待（问题 2）。
5. **放行**：`releasable(D)`。
6. **先停后记**：还没交给承接者的任务邮件当即收回（不会被交出）；H 为空就把第 2–5 步一次提交。否则先停 H 里的会话，等每个都报 `idle`（一轮结束，`acp.turn_ended`）后再一次提交，最多等 10 秒；等待期间被 D 挡住的任务不会被放行。提交之后才投递邮件。

### 4.2 什么会触发撤销

| 事件 | 是否级联 | 停止方 |
| - | - | - |
| 派发者 `cancel_task` | 是 | 派发者 |
| 用户撤任务（`_dev.xsb/tasks/cancel`、`xsb tasks cancel`） | 是 | 用户：派发者被告知 |
| 中枢判任务失败（承接者那一轮出错、承接者被删除） | 是，r 记为 `failed`（`error`），其余记为 `cancelled` | 中枢：没有静默的会话，只有 N 照第 3 步 |
| 承接者完成（回合结束的隐式完结，或 `report_result`，完成或失败） | 否：完成是承接者的事。`report_result` 的返回里列出它为这个任务派出、仍在进行的活，提醒它不需要就撤 | — |
| 用户在会话里停止（Esc） | 是：停下那个会话的工作，以及它正在做的每个任务 | 用户 |
| 退出时选择不继续（abandon） | 已经全部中断，不另做 | — |

### 4.3 分层

```
tools.ts      cancel_task / dispatch_task / start_job：参数、返回文字
kernel.ts     4.1 的事务：裁决、调 doom、组织记录与通知、提交、路由
delivery.ts   提交之后：把通知投进会话，停下只为被撤工作跑的一轮
jobs.ts       提交之后：中止运行中的后台任务

```

## 5. 验收用例

| 用例 | 期望 |
| - | - |
| 撤 P，X 为 P 派出、Z 为 X 派出，B、C 只在为它们工作 | B、C 的工作被停下，确认后 X、Z 一起记为撤销；A 不收回音 |
| 撤 P，中间的 X 已完成，Z 在跑 | Z 被撤，它的承接者被停下；X 的发起方收到 Z 的 `cancelled` 结果 |
| B 同时有 P、Q 时派出 c，撤 P | c 不撤，B 的通知里说明 c 还服务于 Q |
| 接上一行，再撤 Q | c 被撤 |
| 撤 P 时，Y 被 `after` 挡在 P 树里的 Z 后面，且 Y 的承接者空闲 | Y 不被交给承接者，直接记为取消 |
| A 在会话 s1 派 T 并等待，从会话 s2 撤 T | A 撤的，不收回音；s1 的等待去掉 T，不会一直等 |
| 用户撤 P，或在 B 的会话里按停止 | P 的树被撤，停止方是用户；A 收到 `cancelled` 结果 |
| 中枢判 P 失败 | P 的树被撤，A 收到 P 的失败结果 |
| 运行中的后台任务被级联中止 | 不给已被告知的会话送回音；工具仍跑完了的，照常送"已完成" |

## 6. 取舍

- **推断会连错。** 会话里恰好有一个未结束任务时，模型为别的事派出的活也会挂在它下面，撤它时被一起撤。一个 Agent 一次只做一件事，开着的任务通常就是这一轮正在做的那件，这种情况少；连错的后果是多撤，承接者会在通知里看到并能重派。
- **主体只用于归因，不进图。** 停止方、通知的豁免按主体（Agent、用户、中枢）算，但图的节点仍只有任务。用户的 Esc 停的是一个会话手上的任务；将来若要"停掉某个智能体的全部工作"，对它所有会话的任务各撤一次即可，不需要改结构。
- **不丢弃派发者排队中的消息。** 中枢判断不了一条消息是不是关于被撤的任务。

停止已经完成的根任务仍遍历其后代，根的原结果和完成状态不变，记录 `cascadeStopped`。后续支撑者计算不再穿透这个已撤销的根。执行器的停止事件与确认绑定 turn ID；创建子任务在提交前检查已提交的停止状态。具体生命周期见 [TURN-LIFECYCLE.md](TURN-LIFECYCLE.md)。

### 2026-11-26 调用结果与重启结算

普通 Agent 调用结果保存在任务账本，不默认给发起 Agent 回传 prompt，也不因 legacy wake/sync 偏好隐式等待子任务。显式 DAG 控制与依赖释放仍遵循图规则；后台 job 和显式订阅保留各自的通知契约。workflow 的追加工作结果保存到节点 additionalResults，不形成回传 prompt。重启前未确认输入及没有邮件的 blocked 工作统一终结，结束事务不得再释放同一批正在终结的任务。
