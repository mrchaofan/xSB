# 动态角色与转授权

Agents Team 的角色定义是类型，Agent 是实例。持久授权采用「源角色类型 → 目标角色类型」，任务和消息交给具体实例。保留现有 `dispatch`、`message` 两种能力，不增加独立的“授权管理员”能力：能向一个角色类型派发任务，就能向该类型授予权限。

## 为什么授权放在类型上

一个角色可以有多个实例，也可以暂时没有实例。实例级授权会要求为每个新实例重复授权，或者另加类型级默认授权；两套规则需要额外决定覆盖、继承和冲突。类型级授权直接表达「技术负责人可以派活给开发者」，实例增加、删除和重建都不改变团队策略。

任务发起者、消息回复对象仍是实例和会话级关系，但这些是随当前工作产生的临时联系权，不进入持久授权图，也不能转授。没有角色的 Agent 使用 `agent:<id>` 作为独立授权键；它的权限不会被同名角色类型继承。旧配置中的无角色实例键在启动时迁移，已有角色名优先作为类型解释；存在歧义的无角色同名 Agent 需要重新授权。

## 创建与授权流程

所有会话都获得以下 `team` MCP 工具，权限在调用时检查。

| 工具 | 行为 | 权限 |
| --- | --- | --- |
| `list_roles` | 读取角色说明、技能、实例和可用类型授权，包含零实例类型 | 可直接读取 |
| `create_role` | 写入项目自己的新角色定义，可设置说明、后端、MCP 和技能 | 向新类型的 `dispatch` 权限 |
| `create_agent` | 创建指定角色的实例，使用角色后端默认值，否则沿用调用者后端 | 向该类型的 `dispatch` 权限 |
| `grant_permission` | 为受权类型新增 `dispatch` 或 `message` 的目标类型 | 向受权类型的 `dispatch` 权限；授出的能力必须已有 |

没有派发权限时，使用现有 `session/request_permission`，由用户选择「允许一次 / 始终允许 / 拒绝」。允许一次只覆盖本次操作；始终允许把调用者到目标类型的派发边保存到项目配置。新角色没有权限，工具不能覆盖已有角色或实例，也不能通过 `create_role` 直接写入 `grants`。

例如，技术负责人可以创建一个调研员角色，再授权它向开发者派发任务：

```json
{"name":"researcher","description":"调查实现方案","instructions":"收集证据并提出实现建议"}
```

上面是 `create_role` 的参数，然后调用 `grant_permission`：

```json
{"role":"researcher","cap":"dispatch","to":["developer"]}
```

最后调用 `create_agent`，再用现有 `dispatch_task` 派活：

```json
{"id":"researcher-1","role":"researcher"}
```

前提是负责人已获准向调研员和开发者派发任务。结果配置保存的是类型边，第二个调研员实例自动获得同样权限。

## 转授范围与生命周期

受权者获得的权限不能超过调用者同种能力的现有范围。能向开发者派发任务不代表能给开发者发消息；无限制的 `*` 只能由自身已有无限制同种能力的角色授出。能力来源是角色默认 `grants` 和项目的持久 `permissions`，不包含任务发起方或消息回复带来的临时权限。

转授保存为项目中的独立授权边。以后收回授予者的权限不会自动级联撤销已授出的边；用户修改项目策略时应明确调整受权者的边。这沿用当前“始终允许”的持久策略，而非建立依赖授予者存续的委托链。

授权等待结束后再次检查工作代次、角色/实例是否已存在和可转授范围。停止会作废在途操作，即使权限原本已允许，也不能在异步恢复后写入角色、实例或授权。创建角色复用 ACP 编辑界面的 `Hub.putRole`，角色和实例通过既有通知出现在桌面和 CLI 中。
