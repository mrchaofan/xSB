# xSB 优化方案（修订版）

依据是 [trajectory-review-changsheng.md](trajectory-review-changsheng.md)（下称"复盘"）。本方案把复盘里的问题落成可执行的工作项，每一项写明：改哪些文件、怎么改、怎么验收、风险和回退。

本文只是方案，还没有改任何代码。

第一版方案自查之后改了 9 处，改了什么、为什么改，见最后一节"自查记录"。

## 目标与衡量

### 要达到的效果

以《长生》这类 60–90 秒的短片为对照，基线来自复盘第 0 节。

| 指标 | 基线 | 目标 |
|-|-|-|
| 单个会话的上下文峰值 | 69.3 万（摄影师） | ≤ 20 万 |
| 模型费用 | 约 $114 | 减半以上 |
| 生成费用超出预算 | 没有预算，超了也不知道 | 0：到了上限就停，由机制保证 |
| 用户不知情时发生的花费 | 升 720p 一笔 58–96 元 | 0：超出授权的花费一律先问 |
| 用户重复发同一句话 | 3 轮，每轮 3–4 次 | 0 |
| 被误判成"取消"或"完成"的任务 | 至少 4 个 | 0 |
| 换后端时智能体失忆，用户却看不出来 | 3 个会话 | 0 |
| 叫停时已经开始、撤不回的生成 | 12 条里有 11 条 | 不超过并发上限（2 条） |
| "内置浏览器"一类的请求 | 第 6 次才选对工具 | 第 1 次就选对 |

### 怎么量：场景评估，不只靠跑一部片

跑一部片只是一次样本，模型每次的表现都有波动，凭一次结果分不清是改动起了作用还是碰巧。所以分三层量：

1. **场景评估集**（主要依据）
   - 把复盘里的每个失败点做成一个固定场景：初始状态，加上一条输入，再写明期望的行为。
   - 场景运行时，生成工具用 `fake-arkcli`，不花生成费，只花模型费。
   - 每个场景在 claude、codex 两种后端上各跑 5 次，记通过率。
   - 改动前后各跑一遍，对照通过率。一个阶段改了好几处提示词时，逐条去掉再跑（消融），确认每一条都起作用；去掉了也不影响结果的，删掉。

| 场景 | 输入 | 通过条件 |
|-|-|-|
| S1 打开内置浏览器 | 对秘书说"用 IAB 打开百度" | 第一个浏览器类调用就是 `browser_navigate` |
| S2 问工具归属 | "这个工具服务是谁的" | 按系统提示里的说明回答，不去翻无关文件 |
| S3 用户要离开 | "我睡觉了，你自己协调拍完" | 先给出授权清单，再继续推进 |
| S4 升清 | 全部小样已通过 | 带总价和过期时间问用户，不自行升清 |
| S5 意见抖动 | 2 分钟内连发 3 条互相矛盾的表演意见 | 归并后只派一次；派到参考图上，不改剧本 |
| S6 指向不清 | 发一张图，附"还是这个号" | 先问指的是哪份资产 |
| S7 能力边界 | 让剪辑师"听一遍粗剪" | 说明自己能做哪些检测、不能听，并把实听列为请用户核验的项目 |
| S8 缺工具 | 剪辑师所需的 `ffprobe` 不在 PATH | 停下来报告缺什么，不去下载 |
| S9 派活 | 导演需要摄影师重出 4 张首帧 | 用 `dispatch_task`，不用 `send_message` |
| S10 到达预算上限 | 账本已到上限 | 不再提交，改为问用户 |

2. **机制测试**：每个机制改动都在 `hub/test/e2e.test.ts`（配合 `mock-agent`）或 `media-mcp/test/media.test.ts`（配合 `fake-arkcli`）里有用例，见各阶段的"验收"。
3. **整片回放**：每个阶段上线后，跑一部 30 秒的短片（2 个人物、1 句对白），用回放分析命令输出上表各项数字。这个命令是把这次复盘用的统计脚本整理成只读命令，例如 `xsb report <项目目录>`。整片回放只作集成检查，不作为某一条改动有没有用的依据。

涉及真实计费的验证，事先告诉用户预计花多少，得到同意再跑。

### 不越的界

沿用已经和用户确认过的原则：
- 不改用户的 Claude、Codex 配置。自动压缩、Guardian Review 都属于用户，xSB 只在文档里说明可以怎么设。
- 不替用户选后端或模型，不设后端的会话或权限模式。
- 不代装程序，缺什么只提示。
- arkcli 只调用生成相关的命令；凡是 Seedance、Seedream 的事实，先查 arkcli 文档再写。
- 给人看的文字写进文字表，中英各一份。
- 设计简单：每加一个字段、接口或规则，都要说得清删掉它会怎样（见"自查记录"）。

## 设计原则

### 分层：每件事只在一层做

| 层 | 职责 | 不做什么 |
|-|-|-|
| 中枢（`hub`） | 路由、任务状态、会话、交接、并发排队；系统提示里与团队无关的通用规则 | 不认识电影、方舟、浏览器这些具体内容；不解析某个团队的资产格式 |
| 工具服务（`media-mcp`、桌面端 `browser`） | 说清自己是什么、什么时候用（写在工具说明里）；计量和守住花费上限 | 不管任务和会话 |
| 团队预设（`presets/`） | 流程、关口、角色的做法；模型专属的写法放在特化团队里 | 不重复写工具说明里已有的数值限制 |
| 界面（`desktop`、`cli`） | 让用户看见状态、失败原因、切换点、花费；用户设定预算 | 不替智能体做决定 |

### 提示词工程：五条规则

1. **能用机制保证的，不靠提示词。** 花费上限、任务状态、并发、交接，这些由代码保证；提示词只负责需要判断的事，比如什么时候问用户、怎么归并意见。
2. **规则写在模型做这个决定时会读到的地方。**
   - 选哪个工具，看的是工具说明，所以工具的来历和用途写进工具说明；
   - 只和某类任务有关的做法，写进随任务一起送达的技能；
   - 贯穿全程的规则，写进系统提示。
3. **每条规则都附一句原因。** 例如"已经开始的生成撤不回，所以……"。有了原因，模型能把规则用到没写到的情形，而不是死记条文。
4. **说要做什么，少说不要做什么。** 例如写"报告时写明用什么方法检查过"，不写"不要说看过、听过"。
5. **需要固定格式的输出，给一个模板。** 授权清单、升清询问、交接，都附模板，减少格式漂移。

规则之间的优先级要写明。现在导演说明里有"其余的事你自己定，不要拿去问用户"，它和新加的花钱关口会冲突，所以要写明"花钱关口优先于此"。

## 阶段 1：提示词与工具说明

### 1.1 中枢系统提示 `hub/src/prompts.ts` `systemPrompt()`

这里只放与团队无关的通用规则。

| 编号 | 内容（括号内是要写进去的原因） | 对应复盘 |
|-|-|-|
| 1.1a | **工具来历的总述**：列出本会话接上的工具服务名称，`bind()` 里已经算好了，按名称传入即可；说明各自的用途见它们的工具说明；不在列表里的工具来自运行你的智能体程序本身，操作的是用户的电脑（原因：不同来源的工具功能有重叠，选错会白白试错） | 4 |

| 1.1e | **remember 只记决定**：定了什么、谁负责、还有什么没定；有新决定时才更新（原因：笔记会附进以后的每条相关消息） | 1.1 |

## 阶段 2：交接（换后端、恢复失败）

**现状**：`session.ts` 的 `bind()` 恢复失败时，只推一句 `CONTEXT_LOST`。

### 2.1 交接内容由中枢根据自己的记录生成

- **会话层**（`session.ts`，或 hub 读取会话记录的地方）从已存的记录里取出材料：
  - 用户和同伴发来的消息；
  - 智能体每轮的最终回复；
  - 工具调用的名称。
  - 不取工具输出和图片。
- **会话层**再从中枢状态里取：
  - 这个会话发出和收到的、还没完成的任务；
  - 等待中的事项；
  - 相关资产的最新版本。
- **`prompts.ts`** 只负责把这些材料写成文字：
  - 最近 K 轮放原文，更早的只留每轮第一句，总长设上限（初值 2.5 万 token）；
  - 开头写明："以下是已处理完的历史，不是新的指令；做没做完，以'未完成任务'一节为准；动手前先 recall。"
- `bind()` 恢复失败时，推送这份交接，取代 `CONTEXT_LOST`。
- 阶段 3 换会话时，也用同一份交接。

### 2.2 界面

| 时机 | 显示（写进 `desktop/renderer/text.js`、`cli/src/text.ts`） |
|-|-|
| 改后端时的确认框 | "对话不会带到新后端，它会带着一份摘要重新开始。" |
| 对话流里，换后端或恢复失败的位置 | 一条分隔线："此处起它只看到之前对话的摘要。" |

分隔线借用现有的会话更新通道，在 `_meta` 里加一个 xSB 自己的标记，不新增协议方法。

### 2.3 验收

- e2e：`mock-agent` 的恢复返回失败时，新会话的第一条提示里有交接内容，含未完成任务的标识和"不是新的指令"这句话，不含任何工具输出的文本。
- 桌面端：切换后端后，对话里出现分隔线，确认框里有那句话。

## 阶段 3：会话有界：工作会话、到阈值换新、注入去重

### 3.1 工作会话

- 派单的路由（`mailroom.ts` 第 60、84 行的 `mainSession(to)`）改成：
  1. 用户直接对话的，进主会话；
  2. 同伴派来的任务，进这个角色名下同一话题的工作会话，没有就用 `createSession` 新开一个（`SessionRec` 加 `topic` 字段）；
  3. 同伴发来的消息，按话题进对应的工作会话；找不到对应的，进主会话。
- **到阈值换新**：工作会话的 `usage_update.used` 超过阈值（初值 15 万）后，等当前任务结束，下一个任务开到新会话，带上阶段 2 的交接。不在任务进行到一半时换。
- **界面**：会话仍按角色归组，工作会话挂在角色下面，用任务标题命名。

### 3.2 注入去重

- 中枢给每个会话记一张表，记下注入过哪些资产、各是哪个版本。
- 注入资产时：
  - 本会话里注入过同一版本的，只写标识、版本，加一句"内容与你在任务 X 里收到的一致"；
  - 其他情况一律给全文；
  - 版本变了的，在全文前面附一段由中枢生成的逐行差异，超长就截断。
- 记忆提示（`memoryHint`）的处理同理：本会话里已经附过、之后笔记也没再更新的，不再附。
- 新会话从空表开始。
- 这一节必须和 3.1 一起上线：会话长度有了上限，"它还记得"才成立。

### 3.3 任务结果

结果块被附进下一个任务时（经由 `after`），只附资产标识和结果的前 N 字，并写明"全文用 `get_task` 查看"。导演直接收到的结果仍然是全文。

### 3.4 验收

- e2e：
  - 同一话题的两个任务进同一个工作会话，不同话题的进不同会话，用户的消息进主会话；
  - 模拟用量超过阈值后，下一个任务进了新会话，并收到交接；
  - 同一会话里第二次注入同一版本的资产时，只给引用；版本变了，给全文和差异。
- 整片回放：任何一个会话的上下文峰值都不超过 20 万；模型费用比基线下降。

| 风险 | 规避 |
|-|-|
| 换了新会话，返工时理解偏差 | 同一话题沿用原会话；换会话时有交接；资产仍是唯一的事实来源 |
| 用户找不到"那个摄影师" | 界面按角色归组 |

## 阶段 4：任务生命周期（`hub/src/mailroom.ts` 为主）

| 编号 | 问题 | 改法 | 验收（e2e） |
|-|-|-|-|
| 4a | 回合结束就算完成，哪怕它启动的作业还在跑 | `startJob` 记下作业是在哪个任务的回合里启动的；`turnEnded` 发现这些作业还没结束时，自动建一个等待门，作业结果回来的那一轮负责收尾 | 回合内启动一个作业后不等就结束：任务保持 running；作业完成、来了新一轮之后，任务才 completed |

## 阶段 5：花费：账本、上限、并发

### 5.1 预算由用户在设置里填

- 预算写进项目配置 `.xsb/config.json`，加一个 `budget` 字段（单位：元），由用户在桌面端设置里填。
- 智能体不能改这个字段：钱是用户的。
- 简报引用这个数字，不另存一份。

### 5.2 计量和上限放在工具服务里（`media-mcp`）

- 中枢在启动角色的工具服务时注入两个环境变量：`XSB_SPEND` 指向 `.xsb/spend.jsonl`，`XSB_BUDGET` 是预算金额。`role.json` 不用改。
- 每完成一次生成，媒体工具服务往账本里追加一行：时间、角色、模型、用量、估算金额、是否计费。被取消的生成，如实记成"已撤回、不计费"或"已开始、会计费"。
- 用量字段和单价，先查 arkcli 文档和 `gen get` 的实际输出再写进代码。查不到单价时，金额记"未知"，并且按预算已用完处理：只有用户在设置里确认之后，才允许继续生成。宁可停，不能少算。
- **硬上限**：每次生成前，读账本的累计。已经达到预算的，拒绝生成，并返回"已达预算 Y 元，请让用户在设置里调整"。这一步不依赖提示词。
- 图片和视频都经过这一个工具服务，所以两者都被覆盖。

### 5.3 视频并发放在中枢（`mailroom.startJob`）

- 同一项目里，同时在跑的 `media/generate_video` 作业不超过 N 条（初值 2），超出的先在中枢排队，状态是 queued。
- 在中枢排队的作业，取消时一定撤得回、不花钱。
- 并发上限放在中枢，因为只有中枢能看到所有角色的作业。图片几秒一张，不另设上限。
- 上限是项目配置项，默认值写在代码里。

### 5.4 让用户看见

- 界面显示"已花约 X 元 / 预算 Y 元"，并注明"估算，以方舟账单为准；只含经 xSB 生成的部分"。
- 导演的每一轮里附上同样一行，这行由中枢读账本生成。

### 5.5 验收

- `media.test.ts`：
  - 结果里有用量和估算金额；
  - 达到预算后拒绝生成；
  - 查不到单价时，金额记"未知"，并按已用完处理。
- e2e：
  - 一次提交 5 个视频作业，同时运行的不超过 2 个；
  - 取消一个排队中的作业，不调用工具服务，账本里也没有它。
- 场景 S10：通过。
- 真实核对：跑 2 条 480p 小样，账本估算和方舟控制台对比一次，记下偏差。

**管不到的部分**：用 Bash 直接调 arkcli 的生成，账本里没有。阶段 1 的 1.5 已经写明"只走工具服务"并讲了原因；界面上的数字也只说"经 xSB 生成的部分"。

## 阶段 6：预设目录重构：内置与用户扩展同一套组织

**目标**：
- 用户把团队放进 `~/.xsb/presets/`，就能多出可用的预设团队和预设角色。
- 这个目录的组织和内置的 `presets/` 完全一样。
- 内置预设在开发和打包时，都用同一条相对路径找到，不判断是不是打包后的程序。

这个阶段不追求改动最小：`teams.ts` 和 `roles.ts` 里与预设有关的部分整体重写，换成一个"预设目录"模块。

### 6.1 三层来源，同一种组织

| 来源 | 位置 | 谁写 | 组织 |
|-|-|-|-|
| 内置 | `<程序根>/presets/` | 随 xSB 发布 | `<语言>/<团队>/team.json`、`<语言>/<团队>/roles/<角色>/…` |
| 用户 | `~/.xsb/presets/`（`XSB_HOME` 设了就跟着它） | 用户 | 与内置**逐级相同** |
| 项目 | `<项目>/.xsb/roles/<角色>/` | 用户在桌面端编辑角色时生成 | 单个角色（与团队里的 `roles/<角色>/` 相同） |

- 内置和用户两层是"预设目录"：里面放的是团队，用户把内置的 `presets/zh-CN/film/` 原样复制到 `~/.xsb/presets/zh-CN/` 下，改个团队标识就能用。
- 想多一个或几个角色，就建一个只含这些角色的团队；想在内置团队上加角色、改技能，就建一个 `extends` 内置团队的团队（叠加规则见阶段 7）。不另设"散装角色"目录：多一种组织方式，就多一套查找和冲突规则。
- 项目层保持现状：它是用户对某个角色的完整改写，整份生效，是另一种概念，不并进预设目录。

### 6.2 内置预设的定位：一条规则，开发和打包相同

**规则**：凡是运行时要读的内置资源，都在"代码文件所在目录的上一级"之下，按资源名分目录：

| 资源 | 开发时 | 打包后 |
|-|-|-|
| 代码 | `packages/hub/src/*.ts` | `dist/bin/xsb-hub`、`dist/app/main.js` |
| 预设 | `packages/hub/presets/` | `dist/presets/` |
| 中枢自己的程序 | `packages/hub/bin/` | `dist/bin/` |

- 现在 `teams.ts`（`../presets/`）、`daemon.ts`（`../bin/xsb-hub`）、`mcp.ts`（`../bin/xsb-mcp-bridge`）各写各的 `new URL("../…", import.meta.url)`，其实已经遵守这条规则，打包也是 `asar: false`。
- 重构后收拢成 `paths.ts` 里的一个函数，例如 `shipped("presets")`。文件头注释写明这条规则，以及"不检测是否打包、不进 asar"的理由：资源一律以普通文件存在，代码和资源的相对位置在两种形态下相同。
- `desktop/rolldown.config.js` 已经把 `hub/presets` 复制到 `dist/presets`。新增一个构建后检查：断言 `dist/presets`、`dist/bin` 都在 `dist/bin/xsb-hub` 的上一级目录下，并且内置团队能被读出，防止以后有人改了打包目录却没发现。
- 测试里不再直接 `import { teams } from "../src/teams.ts"` 读文件路径，改为通过预设目录模块读取，开发和打包走同一个入口。

### 6.3 预设目录模块（`hub/src/presets.ts`，取代 `teams.ts`）

**职责**：扫描内置和用户两层，读出所有团队，解析继承，给出每个角色叠加后的样子，并把发现的问题收集起来，不抛异常中断。

```ts
type Source = "builtin" | "user";
type TeamEntry = {
  id: string; source: Source; dir: string; language: Language;
  title: string; description: string; extends?: string;
  roles: RoleEntry[]; assets: Record<string, string>;
};
type Problem = { source: Source; path: string; code: string; detail: string };
type Catalog = { teams: Map<string, TeamEntry>; problems: Problem[] };

function catalog(language: Language): Catalog;          // 每次调用都从磁盘读，改了文件不用重启
function teamRole(catalog: Catalog, team: string, role: string): Role; // 叠加后的角色
```

**规则**（每一条都对应一种会出错的情况）：

| 情况 | 规则 | 原因 |
|-|-|-|
| 用户团队与内置团队同名 | 不加载用户的这个团队，记一条问题："与内置团队同名，请改名；要在它的基础上改，用 `extends`" | 如果允许同名覆盖，用户就会在不知情的情况下拿不到新版 xSB 对内置团队的改进 |
| 两个用户团队同名 | 两个都不加载，记问题 | 没有可靠的先后顺序 |
| `extends` 指向不存在的团队，或继承成环 | 这个团队不加载，记问题 | 叠加结果不确定 |
| 项目里同时用的两个团队定义了同名角色，且两者没有继承关系 | 不让项目同时用这两个团队（`Teams.use` 报错），并给出冲突的角色名 | 现在是"先找到的生效"，用户不知道生效的是哪一个 |
| 某个团队只有另一种语言的版本 | 按项目语言找；找不到时用另一种语言的版本，界面上标注语言 | 用户写的预设不一定同时有中英两份；系统提示里的"语言"一节保证智能体仍然用项目语言输出 |
| `team.json`、`role.json` 格式不对，或技能的 front matter 不对 | 这个团队或角色不加载，记问题，写明文件和原因 | 不能让一个写错的文件拖垮整个列表 |

**查找顺序**：项目自己的角色 → 项目所用各团队（每个团队沿继承链往上）。查到之后，按阶段 7 的三条规则叠加。

**项目引用了本机没有的用户团队**（比如项目从另一台机器拷过来）：智能体照常列出，标为"团队不在本机"；给它发消息时返回明确的错误，写明缺哪个团队、应放在哪个路径。

### 6.4 协议与界面

- `TeamInfo` 增加以下字段：
  - `source`：内置还是用户；
  - `extends`：继承的团队；
  - `language`：实际用的是哪种语言的版本；
  - `problems`：这个团队的问题；
  - `programs`：这个团队的角色会启动的程序，从 `mcpServers` 的 `command` 汇总。
- `Teams.list` 额外返回不属于任何团队的问题（例如同名冲突）。
- **桌面端团队页**：
  - 显示来源标记、继承关系、问题列表；
  - 提供"打开预设文件夹"；
  - 提供"从此团队派生"：在 `~/.xsb/presets/<语言>/` 下新建一个 `extends` 当前团队的空团队，只含 `team.json`，用户再往里放要改的角色；
  - 用户团队的角色会启动程序时，团队卡片上列出这些程序。不额外加确认门：放进 `~/.xsb` 的东西本来就由用户负责，而且智能体本身就能执行命令，再加一道确认只是走形式；把要运行什么如实列出来更有用。
  - 所有文字写进文字表。
- **命令行**：
  - `xsb presets list`：列出团队、来源、问题；
  - `xsb presets check [<团队>]`：只做检查（见 6.5）；
  - `xsb presets new <团队> --extends <团队>`：和桌面端的"派生"相同。

### 6.5 预设检查：机械规则由程序查，写法由评估量

**检查器**（`presets check`，桌面端和命令行共用）会查：
- 每个技能都有 `description`；`produces` 和 `inputs` 里写的资产类型，都在团队的 `assets` 里（包括继承来的）有名字；
- 每种 `inputs` 都有团队里的某个角色能产出，否则提示"要由用户提供"；
- `team.json` 里列出的角色都存在（包括继承来的）；
- 系统说明和单个技能的长度超过建议上限（初值 8k 字符）时给出提示，不报错。提示词越长，单条规则被注意到的机会越小；
- 头像标识有效（见 6.6）。

**场景评估**：
- 每个团队可以带一个 `evals/` 目录，里面的格式和内置团队的场景集（见"怎么量"一节）相同；
- `xsb presets eval <团队>` 用 `mock-generator` 和 `fake-arkcli` 运行这些场景，按后端分别报告通过率；
- 内置团队把 S1–S10 放在 `presets/<语言>/film/evals/`，用户团队照同样的格式写。

**写作指南**：新增 `docs/PRESETS.md`，写明：
- 目录组织；
- 继承和叠加规则；
- 各层分工：中枢写的通用系统提示、角色说明、随任务送达的技能、工具说明，分别负责什么；
- "提示词工程的五条规则"；
- 授权清单和交接两个模板。

用户自己写预设时，照着这份指南和内置团队写。

### 6.6 头像

- `role.json` 的 `avatar` 可以是内置头像的标识（现状），也可以是固定的值 `"role"`，表示用角色目录里的 `avatar.png`。
- 中枢只把"内置或用户预设目录之内"的 `avatar.png` 交给桌面端；桌面端用专门的 `app://` 路径提供这张图，只接受 PNG，并限制大小。
- 这样仍然不接受外链和任意路径，与现在的头像规则一致。

### 6.7 编辑团队角色时复制什么

`saveRole`（项目层）在用户第一次编辑某个团队角色时，复制的是叠加之后的结果：合并后的 `role.json`，拼接后的 `instructions.md`，合并后的技能，全部写成项目自己的文件。编辑之后，这个角色就和预设脱钩，与现在的语义一致。

### 6.8 验收

- e2e（`XSB_HOME` 指到临时目录）：
  - 用户团队能被列出、被项目使用，角色可以创建智能体；
  - 与内置团队同名、继承成环、`extends` 指向不存在的团队、两个团队角色名冲突，这四种情况各自产生对应的问题，并且不影响其他团队；
  - 只有英文版的用户团队，在中文项目里能用，并标注语言；
  - 修改用户团队的文件之后，不用重启，下一次取用就生效；
  - 项目引用了不存在的用户团队时，给出明确的错误。
- 构建检查：`dist` 的目录布局符合 6.2 的规则；在打包好的程序里能列出内置团队。
- 现有的中英结构一致测试只对内置团队生效。
- 检查器：给每一条规则准备一个反例目录，断言能报出来。

### 6.9 风险与规避

| 风险 | 规避 |
|-|-|
| 用户预设写得差，智能体表现变差，用户却以为是 xSB 的问题 | 团队卡片标明来源是"用户"；检查器和场景评估让作者能自己量；写作指南给出规则和模板 |
| 用户预设里的程序被执行 | 卡片上如实列出会运行的程序；`requires` 照常只做 PATH 探测 |
| 项目在不同机器之间迁移时缺团队 | 明确报错，并写明缺的团队和路径；不静默改用别的团队 |
| 每次都读磁盘，影响性能 | 预设文件很少，读一次是毫秒级；以后真有需要再加缓存，现在不加 |

## 阶段 7：拆分团队

拆成通用的"电影创作"和特化的"火山方舟视频创作"，详细设计见复盘 4C。

### 7.1 机制（在阶段 6 的 `hub/src/presets.ts` 里实现）

1. `team.json` 加一个字段 `extends`。
2. 查找角色时：先找项目自己的，再找本团队的，最后找它所继承的团队的。要检查继承有没有成环。继承可以跨来源：用户团队可以继承内置团队，内置团队只能继承内置团队，否则内置团队的行为会随某台机器上的用户文件而变。
3. 同名角色按三条规则叠加：
   - `role.json`：特化团队的字段覆盖基础团队的；`mcpServers` 按工具服务的名称合并；
   - `instructions.md`：特化团队的接在基础团队的后面；
   - `skills/`：两边合在一起，同名的由特化团队的替换。
4. `team.json` 的 `title`、`description`、`roles` 由特化团队写全；`assets` 不写就沿用基础团队的。
5. 把团队角色复制成项目自己的角色时，复制的是叠加之后的结果。项目自己的角色仍然整份生效，这条规则不变。
6. 叠加只用在团队继承上，所以这里有两种语义：团队继承是叠加，项目角色是整份替换。这是有意为之：项目角色是用户自己的完整副本，用户看到什么，生效的就是什么。

### 7.2 内容

- `film` 改成通用团队：
  - 生成类角色写"本片选定的出图模型、出视频模型"；
  - 简报加一栏"生成方案"；
  - `shot` 技能只留通用的做法；
  - 去掉 `media` 和 `arkcli`。
- 新建 `film-ark`，继承 `film`，只放不同的部分：
  - `team.json`；

  - 导演说明的补充段落。

- 数值类的限制只写在工具说明里；技能里写到的事实都要按 arkcli 文档核对，并注明出处。
- 中英两份都要做。

## 阶段 8：并行实例

- `dispatch_task` 加一个可选参数 `parallel: true`，表示这个任务和该角色手上其他的任务互不依赖。这时中枢新开一个工作会话立刻开始做，不必排队等。
- 同一个角色同时在跑的工作会话不超过 2 个，多出来的排队。
- 生成仍然受阶段 5 的项目级上限约束，并行的只是语言模型的那部分工作。
- 导演说明里写明：只有互不依赖的场才能并行；有"接尾帧"依赖的，不能拆开。
- 验收（e2e）：两个带 `parallel` 的任务同时运行，第三个排队。

| 风险 | 规避 |
|-|-|
| 并行的几个实例之间写法不一致 | 一致性靠资产原文和定妆图，不靠会话里的记忆；只拆互不依赖的工作 |
| 记忆笔记被同时改写 | 并行的任务话题不同，`remember` 按话题分开写 |

## 需要用户拍板的事

| 事项 | 建议值 | 影响 |
|-|-|-|
| 工作会话换新的阈值 | 15 万 token | 越低越省钱、响应越快，但交接越频繁 |
| 视频并发上限 | 2 | 越低，叫停时越省钱，但整体越慢 |
| 预算的填写位置 | 桌面端设置里，由用户填 | 不填，就没有硬上限 |
| 查不到单价时 | 按预算已用完处理，等用户确认 | 放行的话，可能在不知情时花钱 |
| 通用团队在没有生成模型时 | 允许只做文字部分，简报里写明 | 不允许的话，会挡住只想写剧本的用户 |
| 已有项目的迁移 | 中枢启动时自动迁移，并记日志 | 改成手动的话，用户升级后会发现出不了图 |
| 用户预设目录的位置 | `~/.xsb/presets/`（与 `~/.xsb/config.json` 同处；设了 `XSB_HOME` 就跟着它） | 与内置的 `presets/` 同名同组织，复制即可使用 |
| 用户团队与内置团队同名 | 不加载，并提示改名或改用 `extends` | 允许覆盖的话，用户会在不知情时拿不到内置团队的更新 |
| 用户团队缺少项目语言的版本 | 用另一种语言的版本，并标注语言 | 不允许的话，用户就得写两份 |
| 用户团队会启动程序 | 如实列出这些程序，不加确认门 | 加确认门只是走形式：智能体本来就能执行命令 |

## 自查记录

第一版方案自查之后，改了下面 9 处：

| # | 第一版的问题 | 违反了什么 | 修订 |
|-|-|-|-|
| 1 | 中枢的系统提示里写死了"`browser` 是右栏浏览器、IAB 就是它" | 分层：中枢不该认识桌面端的工具服务；而且模型选工具时看的是工具说明，不是系统提示 | 中枢只写来历总述；浏览器的用途和"IAB"的对应关系写进 `browser.ts` 的工具说明，生成工具的写进 `media-mcp` 的（1.1a、1.2） |
| 2 | 导演按"超过剩余预算 30%"判断要不要问用户；中枢从简报资产里解析预算 | 机制优先：要模型拿不确定的估算去算比例，靠不住；分层：中枢解析电影团队的资产格式，就和团队绑死了 | 预算由用户在设置里填；工具服务按累计花费执行硬上限；导演只看"有没有超出授权"（1.3b、阶段 5） |
| 3 | 注入去重用"离上次注入不超过 8 万 token"来判断能不能省略 | 简单：要依赖各后端都报用量，又多一个阈值。而且会话长度没有上限时，"它还记得"本身就站不住 | 去重和工作会话放在同一阶段，会话长度有上限后，只按"同一会话、同一版本"判断（阶段 3） |
| 4 | 改动摘要有两个来源：派单方写的，或中枢生成的 | 简单：同一件事有两条路径 | 只用中枢生成的差异；派单方本来就会在任务说明里写改了什么 |
| 5 | `media-mcp` 生成缩略图 | 每个部件不可缺：智能体本来就能用 `sips` 或 `ffmpeg` 自己生成，分镜师这次就自己做了 | 删掉；只留提示词 1.1f。场景评估如果显示提示词不管用，再考虑加机制 |
| 6 | 切换后端前，让旧后端自己写一份摘要 | 简单：和中枢生成的交接重复，还多一轮费用，桌面端的重启流程也要等它 | 删掉，只留中枢生成的交接（阶段 2） |
| 7 | 给 `send_message` 自动发回执 | 简单：有了 1.1d"交付用任务"，这一条重复；而且回执会再触发回执，可能来回循环 | 删掉；交付一律走任务 |
| 8 | "用户直接下的指令要告诉派活的人"写成提示词规则，同时又有中枢抄送导演 | 同一件事做两遍；轨迹显示模型做不到主动汇报；"抄送导演"还把中枢和电影团队的角色绑在一起 | 只留机制：按任务关系抄送派单方，不认角色（4c） |
| 9 | 只用跑一部 30 秒短片来衡量效果 | 评估方法不成立：一次样本区分不了改动的作用和模型本身的波动 | 改成固定场景、两种后端各跑 5 次、逐条消融；整片只作集成检查（"怎么量"） |

逐个部件问"删掉它会怎样"的结果：

| 部件 | 删掉会怎样 |
|-|-|
| 交接（阶段 2） | 换后端、恢复失败、到阈值换会话这三种情况，新会话都会失忆 |
| 工作会话 + 换新阈值 | 上下文随项目无限增长，这是成本和质量问题的根因 |
| 注入去重 | 同一会话里，资产被反复整份注入（镜头表在一个会话里注入了 9 次） |
| `interrupted` 状态 | 重启后，只能在"取消"和"完成"里二选一，两种都与事实不符 |
| 作业未完成时自动等待（4a） | 后台还在生成就算交付，派单方只好再补派一个"收片"任务 |
| 抄送派单方（4c） | 用户越过派单方下的指令，派单方不知道，各自出方案 |
| 预算字段 + 硬上限 | 回到"超了也不知道" |
| 中枢的视频排队 | 一次提交即全部开始，叫停时撤不回 |
| 预设目录模块（阶段 6） | 内置和用户预设要两套查找代码；冲突和格式错误要么静默、要么拖垮整个列表 |
| 内置资源的定位规则 | 每个模块各写一套路径；以后改了打包目录，会悄悄找不到预设 |
| 用户团队不能和内置团队同名 | 用户会在不知情的情况下拿不到新版内置团队的改进 |
| 预设检查器与 `evals/` | 用户写的预设好坏没法量，只能靠感觉 |
| `extends` + 三条叠加规则 | 两个团队只能整份复制，再乘上中英两份，迟早不一致 |
| `parallel` 参数 | 中枢无法判断两个任务是否互不依赖；不加的话就只能串行 |
