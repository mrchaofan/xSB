## 1. 反馈一：上下文过长 → 分治 + 压缩

### 1.1 现象与根因

| 根因 | 证据 |
|-|-|
| **每个角色只有一个常驻会话，所有任务都投递到这里**（`mailroom.ts:60/84` 的 `mainSession(to)`） | 美术指导一个会话做完风格、选角、5 个定妆、返工、后缀拆分。每接一个任务，上下文涨 2 万到 10 万 |
| **资产每接一次任务就整份注入一次**（`assets.ts:19`，32KB 以内全文内联） | 分镜师的镜头表（约 1.5 万字）注入 9 次；摄影师 11 条任务每条 19k–38k 字符，占它上下文增长的 36% |
| **读图不限尺寸** | 美术指导每张图约 3k token，71 张合计约 21 万。分镜师先自己压到 640–1000px，每张只要 0.65k token |
| **任务结果原样附进下一个任务** | 导演把上一份报告全文贴进新任务（00:42、00:50 两次重复附上 6-2 报告全文） |
| **remember 每轮整段重写** | 导演 51 次 remember，其中 34 次是重写约 600 字的项目快照 |

长上下文下质量下滑的实证：
- 分镜师忘了用户 20:51 说的"研究所不要街景"，20:48 重出的那批帧里仍带"城市雨窗外"。它声称"逐张看过"，结果被打回两次。
- 美术指导说"夸张版先停掉"，但没有调用停止，两张图照样出完并计费。
- doubao 接手 40 万上下文后，5-1 重拍其实没换提示词（`genb2.sh` 写死了 `_v1.txt`），它却下结论"两次重拍都没改成"。
- 多个角色对用户夹杂英文（"Total 33.02 元, under the cap…"）。

### 1.2 方案 A：按工作开会话（分治）

把"一个角色 = 一个会话"改成**一个角色 = 一个主会话 + 若干工作会话**：

- **主会话**：用户直接对话时用。
- **工作会话**：派单时，hub 按 `topic` 找这个角色名下的工作会话；没有就新开一个。
  - 同一 topic 的返工仍回到原工作会话，保留"topic 跟着有历史的人走"这一原则。
  - 新 topic 开新会话。
  - 工作会话超过阈值时换新（见方案 B）。
- 新会话的起点：系统提示、该角色的记忆摘要、任务本身（资产全文），不带别的任务的历史。

**"自动创建角色"建议做成克隆现有角色，不生成新的角色类型：**
- 导演可以 `dispatch_task` 到 `cinematographer` 并标明"可并行"，hub 为互不依赖的场开多个工作会话。这就是导演说明里已经写着的"同时派给多位摄影师"，现在缺的只是实现。
- 不让模型自己发明新角色。新角色没有经过打磨的 instructions 和技能，质量不可控；角色和后端的选择也属于用户（见 [[user-owned-agent-config]] 的原则）。

**会不会更糟：**

| 风险 | 规避 |
|-|-|
| 新会话丢了"默会"上下文，返工时理解偏差 | 同 topic 复用工作会话；换会话时由旧会话写交接摘要（见 B）；资产仍是唯一的事实来源 |
| 并行实例之间不一致（两个摄影师写法不同） | 一致性本来就靠资产原样复制（character、style_guide 的原文、定妆图），不靠会话记忆。只能拆互不依赖的场，"接尾帧"依赖链不拆 |
| 并行导致生成费用和排队成倍 | 受第 2 节的并发上限和预算闸门约束，并行的是语言工作，不是生成额度 |
| 用户在界面上找不到"那个摄影师" | 界面仍按角色显示；工作会话挂在角色下面，按任务标题列出 |

### 1.3 方案 B：xSB 自己的上下文压缩（不改用户的 Claude/Codex 设置）

自动压缩是用户在后端里关掉的，xSB 不去改这个设置。xSB 只管它投递进去的内容：

1. **注入瘦身**（收益最大、风险最小）
   - 同一会话里已经收到过的资产，如果版本没变，只给标识、版本和一句"内容同你在某任务里收到的 v3"。
   - 版本变了，给全文，并在前面附一段改动摘要（由派单方写，或由 hub 做文本 diff）。
   - 任务结果附进新任务时只附摘要和资产标识，需要全文由接收方自己 `get_asset`。
   - 记忆提示（`memoryHint`）在一个会话里只附第一次。
   - **风险**：模型以为自己"记得"，其实早已滑出注意力范围。**规避**：只在同一会话、且离上次注入不超过一定 token 量时省略；换会话后一律给全文。
2. **到阈值就换会话，而不是压缩**
   - 工作会话的已用量超过约 15–20 万（看 `usage_update.used`；分镜师和美术指导在 10 万时响应还在 1–3 秒）时，当前任务结束后，hub 请它写一份交接摘要（已定事项、在做的事、未决事项、关键资产标识及版本），用 `remember` 存进该 topic 的笔记。下一个任务开新会话。
   - 不在任务中途换，避免把半截的工作切断。
   - **风险**：交接摘要漏了东西。**规避**：交接摘要只记"决定"，事实全在资产里；新会话第一句提示它先 `recall` 再动手（`CONTEXT_LOST` 的现成文字可以复用）。
3. **后端切换时也走交接**：这次切到 codex 时三个会话都没能恢复，等于失忆。详见第 4A 节，那里和这里共用一套交接。
4. **看图走缩略图**：提示词规定审片先看不超过 1024px 的缩略图或抽帧拼图，需要细看时再裁局部看原图。也可以给 hub 加一个出缩略图的工具（`ffmpeg`、`sips` 都已有）。读图是后端自己的工具，xSB 管不了尺寸，只能从提示词和工具两头引导。

## 2. 反馈二：成本高 → 先对齐预算、控并发、全部确认后再升清

### 2.1 现象与根因

| 现象 | 证据 | 根因 |
|-|-|-|
| 用户第一次提成本是在 02:39（"成本超预算了"），此前从没约定过金额 | `brief/changsheng` 的"预算与底线"一栏只写了"每镜最多 3 轮" | **简报模板把"预算"定义成重拍轮数**（`brief/SKILL.md` 的例子是"每镜最多三轮"），导演说明里"超出简报的预算时问用户"这条规则永远触发不了 |
| 用户睡觉时，导演自己批了升 720p，一次提交 11 条，花了 **58–96 元**，占全片的 42–55% | 00:44 导演："抢在过期前…先升到 720p 存好，花费上限 100 元"；22:08 它自己说过"这个口要你来开"，02:26 又把"交付 720p 还是 1080p"列为待用户决定 | 关口标准不一致：新建端点（约 10 元）要用户批，100 元的升级它自己定。"过期"被当成了绕过关口的理由 |
| 叫停时钱已花完 | 02:39 取消时 12 条里已跑完 11 条，只省下约 5–8 元 | 批量一次全提交给方舟，取消只能撤掉排队中的 |
| 汇报的花费数字前后打架 | 02:45 说"约 63 元"，03:06 说"没有新花费"，03:12 改成 120–160 元；摄影师说过"出图首张免费、0 元" | 没有账本，靠模型心算和猜 |
| 生成是假并发 | 美术一批 9 张图，耗时从 40 秒到 466 秒依次拉长；分镜一次 12 张以上，最长 1015 秒 | 一次塞满，在提供方那边排队 |
| 分镜帧全部 2560×1440，视频却只出 480p | 53 张分镜帧共 355MB | 出图不分草图和定稿 |

### 2.2 方案

**① 开工前对齐预算（提示词，零代码）**
- `brief/SKILL.md` 的"预算与底线"改成两栏：
  - **生成费用上限**（元），必填，并写明交付分辨率；
  - **最多重拍几轮**。
- 导演按镜头数给一个估算区间请用户确认，例如"约 20 镜 × 480p 小样 × 平均 1.5 次 ≈ X 元，正式版另加 Y 元"。
- 单价从 `arkcli` 文档或已跑任务的 usage 实算，不凭印象写（见 [[seedance-arkcli-docs]]）。
- 试拍之后必须带着实测单价重估全片，超过上限就问用户。现在说明里有这条，但因为没有金额，等于失效。

**② 账本（媒体工具服务 + hub）**
- `generate_video` 和 `generate_image` 的结果里带上本次的 usage（tokens 或张数）和按文档单价算出的估算金额，明确标为"估算"。
- hub 按项目累计，在导演每一轮的提示里附一行"已花约 X 元 / 预算 Y 元"，界面上也显示。
- **风险**：估算和平台账单有出入。**规避**：始终叫"估算"，结项时提示用户去方舟核账；宁可估高。

**③ 花钱的关口写死（提示词 + 工具）**
- 以下三种情况，一律 `ask_user` 等用户确认，"快过期""赶时间"都不算例外：
  - 改交付规格（分辨率、时长）；
  - 一次提交的估算超过剩余预算的一定比例（比如 30%）；
  - 累计花费将超出预算。
- 用户说"我去睡了，你自己协调"时，导演必须先给一张**离开前授权清单**，确认后才能自主推进：本段可花的金额上限、可以自定的事、必须等用户的事（如新建端点、升清）。这次导演为 Seedream 端点白等了 5.5 小时，也是因为没提前拿到授权。
- **风险**：用户不在时进度卡住。**规避**：授权清单就是为这种情况准备的，在额度内可以照常推进；卡住的只是用户事先没批的事，这比花掉不该花的钱好。

**④ 控并发（媒体工具服务或 hub 的 job 层）**
- 每个项目设"同时在提供方那边跑的生成"上限，例如视频 2–3 条、图片 3–4 张，超出的先在 hub 里排队。
- 在 hub 排队的，取消时百分之百不花钱，也不依赖方舟的取消语义。这直接对应"导演根据制片人意见叫停时已经停不住"的问题。
- 批量任务先跑 1–2 条验证提示词和参数，再放后面的（提示词同步写进 `shot/SKILL.md`）。
- 任务按镜头拆开，不要一个任务包 12 条 edit。
- 取消后回报实际省了多少、哪些仍会计费（`media-mcp` 已经会区分"已撤回、不计费"和"已开始、会计费"，只是要汇总给导演）。
- **风险**：总耗时变长。**规避**：上限可配置；而且这次的并发本来就是假的（提供方在排队），实际损失很小。

**⑤ 所有低清小样确认后，再统一确认升清（流程和提示词）**
- 在导演流程表里把"正式版"拆成一个独立关口，排在全部小样审完之后：
  1. 导演整理一张清单：每镜小样的标识、是否通过、升清方式（edit 还是重新生成）、单价；
  2. 汇总成总价，一次性请用户确认；
  3. 用户确认后再派升清。
- 方舟生成结果的地址会过期，这是导演"抢在过期前"自批的理由。不能因此绕过用户，而是把期限摆进询问里："这 11 条小样的地址将在 HH:MM 过期，过期后升清只能重新生成，约多花 Z 元。现在升（约 X 元）还是不升？"由用户决定。
- 分镜帧和定妆候选也分草图和定稿：草图用 1024×576，选定后再出高清。

## 3. 反馈之外的问题（按影响排序）

### 3.2 用户越级直接找下属，导演不知情

- 用户直接对美术说"男使用m1"、对摄影师说"不要重拍…差不多得了"、对编剧说"成本超预算"，导演都不知道。
  - 编剧对"超预算"没有回应，反而把剧本加长了 2 秒。
  - 编剧和导演还各出了一套"碰面"方案。
- **建议**（各角色的通用规则，写进 `prompts.ts` 的 Working with the team）：用户直接给你的指令照做；凡是会影响别人或改变已定事项的，做完用 `send_message` 告诉派你活的人（通常是导演）。hub 也可以把"用户直接发给某角色的消息"抄一份摘要给导演。
- **风险**：导演收到大量抄送，上下文又被撑大。**规避**：只抄一行摘要；导演正忙时合并成一条。

### 3.3 能力边界没写，导致虚报

- 剪辑师说"我从头到尾看过、听过一遍"，其实听不到声音；导演据此派单，把剪辑师当成"能看能听的人"。
- 导演看不了 mp4。
- 粗剪里人物镜头用分镜静帧占位，却没有标注。用户 02:30 看到后说"人物的戏就是静态图片"，其实那时人物镜头一条都还没拍：人脸首帧被平台审核拦了，摄影师 21:35 已经报告过。
- **建议**：
  - `prompts.ts` 加一条：只说你实际做了的检查，比如"用 ffprobe 检测有音轨""抽 6 帧看过"，不要说"看过、听过"；需要人耳人眼判断的，列为请用户核验的项目。
  - 剪辑技能加一条：占位镜头必须在画面上标"占位"，交付说明里也要列出来。
  - 导演说明加一条：给用户看的东西有占位或已知限制时，必须先说明。

### 3.4 意见抖动直接变成版本，剧本 50 分钟改了 7 版

- 18:55–19:45 是"欲 → 痛苦 → 娇喘 → 更夸张 → 撤回"这一连串意见，每条都立刻派给编剧和美术，剧本 v3–v9 就是这么来的。
- 19:44 用户说"还是这个号（好）"，指的是定妆图，导演当成剧本的意见，派出了 v8。之后又把 v7 原样登记成 v9，代写了编剧的资产。
- **建议**（导演说明）：
  - 表演分寸、表情这类主观要求，在参考图或小样上迭代，请用户从已有的几张里挑，不改剧本；
  - 用户连发几条意见时，先归并成一条再派；
  - 意见指向不清（是哪份资产）时先问；
  - 版本号由 `put_asset` 分配，派单时不写死"v7"（这次 v6、v7 已被占用，最后只好登记成 v9）；

## 4. 补充问题：分不清"内置浏览器"和别家的工具

### 4.1 发生了什么（秘书会话 05:12 和 06:44）

1. 用户说"使用 iab 打开百度"。Codex 自带的电脑操控插件 `cua_repl` 里恰好也有一个叫 `iab` 的浏览器（`cua.createBrowserTab("iab", …)`），那是 Codex 应用自己的内置浏览器，在 xSB 里不存在，所以返回 `The browser access host is unavailable`。
2. 插件的说明写着"Use `cua_repl` for all UI actions"，于是智能体先在它里面试了 5 次，每次都过一轮 Guardian Review，还去连了用户的 Edge（`Ambiguous app identifier`）。最后才改用 xSB 的 `browser_navigate`，一次成功。剪辑师 05:08 也走了同一条弯路，卡了约 16 分钟。
3. 用户问"这个工具服务是谁的"，智能体去读了 `~/.codex/skills/.system/openai-docs/SKILL.md` 这个无关文件，最后的回答带着"不能断言"。

### 4.2 根因

- **xSB 的系统提示（`prompts.ts`）只介绍了 xsb 这一个工具服务**。对右栏浏览器（`browser`）、生成工具（`media`）、后端自带的工具，一个字都没说。智能体只能从工具名去猜它们的来历。
- **名字撞车**："IAB""内置浏览器"在 Codex 的语境里有自己的含义。
- `browser_navigate` 的说明写的是"the browser of the app's side panel"，没点明 app 是 xSB，也没说"用户说'内置浏览器、IAB'指的就是这个"。

### 4.3 方案

在 `systemPrompt()` 里加一节"你的工具从哪来"，**按这个会话实际接上的工具服务自动生成**，不手写，保证不会和实际情况不一致：

```
# 你的工具从哪来
- xsb：xSB 中枢，用于团队协作、任务、资产、记忆。
- browser（仅在桌面端接上时出现）：xSB 应用右栏的浏览器，用户能看到也能接手。
  用户说"浏览器""内置浏览器""右栏浏览器""IAB"时，都指它。
- media：xSB 的出图和出视频工具，背后是火山方舟的 arkcli，按量计费。
- <角色在 role.json 里声明的工具服务>：……
- 除此之外的工具都来自运行你的智能体程序（Claude Code 或 Codex）本身，
  比如操作用户电脑上的应用。只有用户点名要操作他电脑上的某个应用
  （如 Edge、QuickTime）时才用它们。
被问到某个工具是谁提供的，按这一节回答，不必去翻别的文件。
```

同时：
- `browser.ts` 中工具说明的开头改成"xSB 应用右栏的浏览器……"。
- `browser_navigate` 失败时，返回的错误信息要说明下一步怎么做，比如"右栏浏览器只在 xSB 桌面端运行时可用"。

**会不会更糟：**

| 风险 | 规避 |
|-|-|
| 用户真想操作自己的 Edge 或桌面应用，却被引到右栏 | 规则只认"内置、右栏、IAB、浏览器"这几种泛称；用户点名某个应用时照常用电脑操控工具 |
| 在命令行里用、没有桌面端时，说明里写着一个不存在的浏览器 | 这一节按实际接上的工具服务生成，没接上就不写 |
| Codex 应用的用户确实想用 Codex 的 IAB | 在 xSB 里它本来就不可用（这次实测返回 unavailable），映射到右栏不会损失能力 |
| 系统提示变长 | 只多五六行，远小于一次资产注入 |
| 和后端插件"所有 UI 操作都用 cua_repl"的说法冲突 | 用户的系统提示优先级不低于插件说明；而且这里的规则只说"右栏浏览器用 browser"，不否定插件对桌面应用的用法 |

## 4A. 补充问题：中途换后端，对话不迁移，用户也看不出来

### 4A.1 现在怎么走（`hub/src/session.ts:118-144`）

1. hub 拿旧的会话标识，到新后端里恢复（`session/resume` 或 `session/load`）。从 claude 换到 codex 时，codex 里没有这个会话，恢复必然失败。
2. 失败后新开一个空白会话。这时新会话只拿到三样东西：
   - 系统提示；
   - 记忆摘要（最多 30 条笔记）；
   - 一句 `CONTEXT_LOST`，意思是"之前的对话没恢复，先 recall"。
3. 旧对话的正文、工具结果、讨论过的细节，都不会迁移。

这次 04:42–04:50，导演、摄影师、剪辑师三个会话都走了这条路，日志写的是 `backend session … not restored (Internal error), starting a new one`。导演上下文从 228947 掉到 19666，那不是压缩，而是从零开始。

注意：导演 03:55 换到 doubao 模型时没有丢上下文，用量一直接着涨。丢上下文只发生在换后端程序时。

### 4A.2 为什么用户感觉不到

- **界面照常显示整段旧对话。** 那是 hub 自己存的记录，不是智能体还记得的东西。用户看着历史都在，就以为它也记得。
- **确认框没提记忆的事。** 改后端时的确认框只写"会重启后端进程、当前这一轮会失败"（`desktop/renderer/text.js` 的 `agent.restarts`、`restart.body`），没说"它会忘掉之前的对话"。
- **对话里没有标记。** 换后端的地方既没有分隔线，也没有提示。

### 4A.3 这次的实际损失

- 导演靠 recall 和查资产找回了状态，但之前算错的花费也照样带了过来。
- 剪辑师在新环境里，原先的抽帧工具解码失败，只好重做整套工具。
- 用户 04:13 直接对摄影师说的"差不多得了"，导演换后端后无从得知。

### 4A.4 方案

1. **由 hub 根据自己的记录生成交接，作为新会话的第一条提示。** 这一步总能做到，不依赖旧后端还活着。
   - 内容：用户和其他角色发来的消息、它自己每轮的最终回复、工具调用的名称。工具输出和图片不带。
   - 篇幅：最近几轮放原文，更早的压成摘要，总量设上限（约 2–3 万 token）。
   - 末尾附 hub 掌握的权威状态：未完成的任务、等待中的事项、相关资产的最新版本。
2. **旧后端还正常时，切换前先让它写一份交接摘要存进记忆。** 它比机器拼出来的更知道重点。旧后端已经坏了（比如这次的 `Internal error`、未登录）就跳过这一步，只用第 1 步。
3. **让用户看得见。**
   - 确认框写明"对话不会带到新后端，它会带着一份摘要重新开始"。
   - 对话里插一条分隔线："此处起换为 codex，之前的内容它只看到摘要"。
   - 同后端恢复失败时同样显示这条分隔线（这次的 `Internal error`、`session in use by another Codex client` 都属于这种情况）。
   - 文字写进文字表，中英文各一份。
4. **与 1.3 共用一套交接。** 到阈值换会话、换后端、恢复失败，都是"旧会话没了，新会话要接上"，用同一份交接格式和同一段提示，不各做一套。

### 4A.5 会不会更糟

| 风险 | 规避 |
|-|-|
| 旧消息里的"开始生成""重拍"被新会话当成新指令再执行一遍，重复花钱 | 交接里写明"以下是已处理完的历史，不是新指令"；做没做完以 hub 的任务状态为准，不以历史文字为准 |
| 旧的工具输出、网页内容里夹带的指令被重新注入 | 只带消息和最终回复，不带工具输出 |
| 交接太长，一换后端上下文又爆了 | 设上限，超出部分只留摘要 |
| 摘要漏了细节 | 事实都在资产库里，交接只管"定了什么、在做什么、在等什么"；新会话动手前仍要先 recall |
| 切换前让旧后端写摘要，要多花一轮的钱和时间 | 只在旧后端正常时做；这一轮很短，远比失忆后返工便宜 |

## 4B. 生成模型的约束该放在哪一层

### 4B.1 现状

- 现在只接了火山方舟。媒体工具服务的登记表里只有 `{ seedance }` 和 `{ seedream }` 两项（`media-mcp/src/server.ts:24-25`），三个出图出视频角色的 `role.json` 也把它们写死了。
- 团队提示词写死了"只有出图和出视频才调用 `media` 工具"。
- 用户自己提供的生成技能大概率不会被用上。证据是：换到 Codex 后，四个角色的技能列表里都有 Codex 自带的 `$imagegen`，一次都没被调用过。

### 4B.2 评估："技能不限制具体方式，只要求是出图或出视频模型"是否合理

**结论**：作为技能的写法合理；作为智能体每次调用都能自己挑模型，不合理。

**为什么技能不该写死具体方式：**
- **写死也没管住。** 摄影师照样绕开 `media`，用 Bash 调了 184 次 `arkcli`，还有 3 次直连接口。能约束住的是机制，不是提示词里的名字。
- **写死挡掉了用户自己的模型。** `$imagegen` 和用户提供的模型技能都被压下去了。
- **两类知识混在一起。** 通用拍摄方法（先小样后正式、一镜一个动作、靠首帧保持一致）和某个模型的限制（Seedance 认"镜头1…镜头2"、拒绝真人人脸首帧）都写在 `shot` 一份技能里。
- **模型选择属于用户。** 这和"不替用户选后端、模型"是同一条原则。

**为什么不能让智能体自由挑：**
1. **链路会断。** Seedance 只接受本账号下方舟模型生成的人脸图作首帧。7-1 的首帧就因为"可能含真人"被拦，后来靠 Seedream 重出首帧才过。分镜师用别家出首帧、摄影师用 Seedance 出视频，人物镜头会全部被拦。
2. **全片不一致。** 不同模型对同一段描述画出的不是同一张脸。
3. **选项一多就选错。** 第 4 节"打开百度"那次就是两个都能用的工具让智能体试错了 5 次。
4. **钱管不住。** 账本、并发上限、排队中撤回都只在统一入口里才做得到。Bash 直调时，xSB 看不见也撤不回。

### 4B.3 原则

- **团队技能只写通用方法**，写"用本片选定的出图模型、出视频模型"。
- **选哪个模型由用户在简报阶段定一次，全片不变**，每种产出一个；能不能衔接，靠技术预检验证（3.5）。
- **模型自己的写法和限制跟着模型走**：数值类限制放在工具说明里，由提供方按实际模型给出；写法和陷阱放在模型自己的技能里。
- **管不住的事要说实话。** 用户的模型接成提供方时，账本、并发、取消照常有效；只通过技能使用时，xSB 管不到花费和取消，简报和界面要写明，并要求每次调用后报告用量、说明能否取消。

这条原则落到团队预设上，就是下面的拆分。

## 4C. 拆成两个团队：电影创作（通用）与火山方舟视频创作（特化）

### 4C.1 现有机制的约束

- 角色按名字整体查找：先找项目自己的，再按项目配置里 `teams` 的顺序找团队（`roles.ts` 的 `sources`）。找到哪份就整份生效，不按技能合并。
- 团队之间没有继承（`teams.ts`）。
- 中英文两份预设必须结构一致，由测试守着。
- 现在的 `film` 团队里，方舟专属内容很集中：
  - `cinematographer/skills/shot/SKILL.md`（10 处）；
  - 三个出图出视频角色的说明里提到 `media` 的几句，以及 `reference-image`、`storyboard`、`casting` 技能里的零星几处；
  - 三个 `role.json`；
  - `team.json` 里 `arkcli` 的 `requires` 和团队描述。
- 导演、编剧、剪辑师的提示词里没有方舟专属内容。

### 4C.2 三种拆法

| 拆法 | 做法 | 问题 |
|-|-|-|
| 两份完整副本 | `film` 和 `film-ark` 各有 7 个角色的全部文件 | 通用内容复制两份，再乘中英两份；改一处要改四处，迟早不一致 |
| 叠两个团队 | 项目配置写 `["film-ark", "film"]`，特化团队只放 3 个出图出视频角色 | 角色整份生效，所以这 3 个角色的说明和全部通用技能（选角、定妆、风格、镜头表、分镜……）仍要整份复制；另外 `team.json` 列出别的团队的角色，现有代码对不上 |
| **特化团队基于通用团队，只放差异（推荐）** | `film-ark` 声明 `"extends": "film"`，只放和通用团队不同的文件 | 要加一个很小的机制（见下） |

### 4C.3 推荐方案

**机制：只加一个字段、三条合并规则。**

- `team.json` 加 `extends`。项目用 `film-ark` 时，角色查找顺序变成：项目自己的 → `film-ark` → `film`。项目配置里只写 `["film-ark"]`。
- 同名角色在特化团队里出现时，与基础角色**叠加**，不整份替换：
  1. `role.json`：特化的字段覆盖基础的；`mcpServers` 按工具服务的名字合并。
  2. `instructions.md`：特化的内容接在基础的后面。特化说明只补充事实，不推翻通用流程。
  3. `skills/`：两边合在一起；同名的由特化的替换。
- `team.json` 里的 `title`、`description`、`roles`（含 `requires`）由特化团队自己写全，因为团队名称、描述、需要的程序都不同。`assets` 不写就沿用基础团队的。
- 用户在桌面端编辑某个角色时，现在会把团队角色复制成项目自己的。改成复制"叠加之后的样子"，项目自己的角色仍然整份生效，这条现有规则不变。

**通用团队 `film`（电影创作）：**
- 7 个角色、流程、关口全部保留。
- 出图、出视频的步骤改成"用本片选定的模型"：
  - 简报加一栏"生成方案"：出图和出视频各用什么，通过什么接入（工具服务还是技能），花费和取消是否受 xSB 管控；
  - 技术预检验证这条链路能走通（含人脸首帧和对白口型）。
- `shot` 技能只留通用方法：提示词的结构、一镜一个动作、五种保持一致的办法（首帧、文生、参考图、接尾帧、首尾帧）、先小样后正式、自检、报告用量。参数怎么对应，写成"按所选模型的说明"。
- `role.json` 不声明任何生成工具服务；`team.json` 不要求 `arkcli`。
- 团队描述写明：出图、出视频需要用户自己提供模型（工具服务或技能）。

**特化团队 `film-ark`（火山方舟视频创作），基于 `film`，只放差异：**

| 位置 | 内容 |
|-|-|
| `team.json` | 名称、描述（出图 Seedream、出视频 Seedance，经 `arkcli`）；三个出图出视频角色要求 `arkcli`，摄影师和剪辑师要求 `ffmpeg` |
| `art-director`、`storyboard-artist`、`cinematographer` 的 `role.json` | 声明 `media` 工具服务（`seedream`、`seedance`） |
| 新技能 `seedance`（摄影师） | 提示词写法（按版本认序号还是时间段）；五种办法对应到 `first_frame`、`reference_images`、`last_frame_output` 等参数；用了首帧不传 `ratio`；只信任本账号模型生成的原图，用户真人照片怎么办；edit 升清路线及其单价；结果地址的有效期 |
| 新技能 `seedream`（美术指导、分镜师） | 草图尺寸（如 1024×576）和定稿尺寸；水印；格式 |
| `director/instructions.md`（接在通用说明后面） | 新建接入点必须用户亲自批，要列进离开前授权清单；技术预检必须测人脸首帧；升清关口里写明小样地址的过期时间；单价以 `arkcli` 文档为准 |

- 数值类限制（时长、分辨率、参考图张数、请求大小）只写在 `generate_video` 和 `generate_image` 的工具说明里，由提供方按实际模型给出，技能里不重复写。
- 技能里写的事实都要按 `arkcli` 文档核对（见 [[seedance-arkcli-docs]]）。

**已有项目的迁移：**
- 现在用 `film` 的项目（包括这次的 `sbws`）实际都是按方舟在做。拆完后 `film` 变成通用团队，这些项目会突然失去生成工具服务。
- 所以拆分时，把项目配置里的 `"film"` 一次性改成 `"film-ark"`，配置的 `version` 从 1 升到 2。只改这个项目自己的 `.xsb/config.json`，不碰任何后端配置。
- 智能体的角色名不变（还是 `cinematographer` 等），`agents.jsonl` 不用改。

### 4C.4 会不会更糟

| 风险 | 规避 |
|-|-|
| 已有项目升级后突然不能出图出视频 | 配置迁移把 `film` 改成 `film-ark`；迁移只改团队标识 |
| 用户选了通用团队，却没提供任何模型，做到分镜才发现出不了图 | 简报的"生成方案"一栏写不出来，就不能定稿；技术预检会在写剧本前失败，并说明缺什么 |
| 通用技能变抽象，方舟用户的生成质量下降 | 方舟用户用的是 `film-ark`，具体写法都在 `seedance`、`seedream` 技能里，内容一点没少，只是换了位置 |
| 叠加规则让人看不清某个角色最后长什么样 | 桌面端和 `inspectAgent` 展示叠加之后的完整说明，与现在"系统说明预览"一样；规则只有三条 |
| 特化说明和通用说明互相矛盾 | 规定特化说明只补充事实、不改流程；测试检查特化团队里有没有与基础团队同名、但内容只是复制的文件 |
| 模型限制在技能和工具说明里各写一份，日后不一致 | 数值只写在工具说明里，技能只写写法和陷阱 |
| 中英文和两个团队的内容成倍增加 | 特化团队只放差异，文件很少；中英结构一致的测试扩展到 `film-ark` |
| 以后再加一家（如用户自己的模型）又要复制一套 | 同样的做法：再建一个基于 `film` 的特化团队，只放这家的 `role.json` 和模型技能 |

## 6. 建议的先后顺序

1. **纯提示词、零风险、立竿见影**：
   - 简报加金额预算；
   - 花钱关口和离开前授权清单；
   - 升清作为独立关口；
   - "你的工具从哪来"一节；
   - 能力边界和安全规则；
   - `dispatch_task` 与 `send_message` 的用法区分。
   这几条能直接避免这次最贵的那笔 58–96 元，以及"继续"重复说好几遍的一部分。
2. **注入瘦身和缩略图**：改动小，直接减少上下文和模型费用。模型费用才是最大的开销。
3. **换后端的交接和分隔线**：用户看不出智能体已经失忆，这比失忆本身更危险。
4. **任务生命周期修正**：有后台生成时不算完成；插话不算取消；`send_message` 有回执；失败显示给用户。
5. **账本和并发上限**。
6. **拆成通用和火山方舟两个团队**：宜与第 1 步的提示词改动一起规划，免得同一批文件改两遍；但要先做配置迁移，再切换 `film` 的内容。
7. **工作会话、到阈值换会话、克隆角色并行**：收益最大，但改动也最大，宜在 1–6 稳定后做。
