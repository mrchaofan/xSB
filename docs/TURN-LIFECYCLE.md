# 多 Agent 任务与 turn 生命周期契约

2026-11-21。规范状态：运行时契约；模型会话说明包含必须遵守的摘要。

本契约约束 Hub 内核的输入、执行与取消。文中的历史工具名标识内核操作。当前主会话与任务会话的模型工具和交付规则见[会话与工作流](WORKFLOWS.md)。

## 1. 核对结论与证明边界

存储提交采用失败屏障：任一日志写入失败后，Hub 撤销执行入口并退出，下一次启动先补全 WAL、再重建状态。旧实例不能继续提交。正常结束和重启结算将输入邮件消费、任务结局、结果通知及依赖释放放在同一事务中。工作流用户停止将图暂停、整个作用域的停止代次、任务冻结、旧待办撤销统一提交，再异步取消后端；在途输入仍按真实回执结算。清空上下文将 session 重置和 `cleared` 边界一起落盘。项目移动保持会话 ID，以 `project_moved` 交接在新目录继续，已执行输入不重放。

按事件数归纳证明状态转移安全、按调用路径长度归纳证明停止传播可达，方法成立。xSB 采用这两组不变量约束任务开启和结束，运行时负责强制执行，模型负责使用正确的工具与诚实报告结果。

应用证明时必须明确定义：

- **turn 与 task 不同。** turn 是一次串行模型执行及其输入；task 是持久化的业务任务。task 可以等待多个 turn，也可以在 turn 尚未退出时通过 `report_result` 结束。一个 turn 可以承接多个仍开放的任务。
- **turn 与 run 不同。** run 是后端一次执行，以 ACP `running`（或首次 `requires_action`）开始、`idle` 结束；turn 是中枢授权的输入和任务归属。已提交 prompt 的 turn 认领随后开始的 run；已有无主 run 只有在当前 turn 的输入获得插入回执后才被认领，认领前的输出保持回合外。running 本身不证明输入已被接收。
- **投递表针对已获授权、依赖已满足且需要执行的 prompt。** `lazy` 邮件留在 inbox；`after` 未满足的 task 留在 blocked；它们属于待办，不因接收请求就立刻开 turn。
- **抢占权限是前提。** `dispatch` 权限不等于任意停止其他发起方的工作。混合所有者的 turn 若无法整体合法停止，抢占请求整体排队，不先取消一部分。请求也不能通过停止祖先把自身工作撤掉。
- **传播可达不等于所有后代都要取消。** 内置 `spare` 策略下每个实际调用后代都参与判定；只为停止范围而存在的后代取消，仍被无关活任务支撑的共享后代保留。`after` 是次序边，不能当成调用/取消边。可信扩展若显式采用 `force`，属于另一个传播策略，须单独说明授权与证明，不能声称满足这里的共享保留规则。
- **逻辑失效与后端退出分开。** 停止决定先持久化并冻结执行权限；后端确认 idle 或被隔离后才启动后继。停止确认期间可以没有有效执行 turn，不能同时启动两个后端工作。

这些约束将简化伪代码细化为实际产品语义。归纳证明覆盖状态安全、输入归属和传播覆盖；模型能否正确完成任务、外部程序能否及时返回、外部写入是否只执行一次，还需要独立的执行与恢复约束。

## 2. 开启与投递规则

插话归入处理时的当前 turn；抢占撤销旧执行资格，并使这次投递优先开启新 turn；排队项从队头取出后直接成为新 turn 的输入。

| B 状态 | 投递方 | 请求抢占 | 行为 |
| --- | --- | --- | --- |
| 空闲 | 任意 | 任意 | 开新 turn；用户输入使其受保护 |
| 有 turn | 用户 | 任意 | 插话；接收时立即保护当前 turn（提升为用户级） |
| 有受保护 turn | Agent | 任意 | 排队 |
| 有未受保护 turn | Agent | 否 | 插话：任务和消息归入当前 turn，不改变保护状态；任务结果不插话，排队；`lazy` 投递仍留在收件箱 |
| 有未受保护 turn | Agent | 是 | 目标 ID、权限及整体停止范围校验通过后抢占；否则按上一行插话 |

**受保护即用户级。** 用户开启或插话过的 turn 属于用户：其他 Agent 的投递只能排队，不能插进去。Agent 发起且用户未插话的 turn 属于 Agent，任何 Agent 的投递都插话。路由时判定一次；插入提交点（`LiveSession.steer`）再次检查保护状态，期间用户已插话则改为排队。

**保护状态属于当前 turn。** 不能用初始发起方替代 `turn.protected`。Agent 发起的 turn 收到用户插话后仍是同一个 turn，但立即受保护，保护不等模型读取后才生效。

上下文恢复期间即使工具调用被暂停，用户插话仍归当前逻辑 turn，并立即保护它。绑定或恢复完成前已收到的用户纠正合并进首个模型请求，不能先执行旧指令再补交已知约束。

抢占使用 `dispatch_task(onBusy="replace", target_turn_id=...)`。模型通过 `list_agents` 获取快照，运行时在提交停止决定前再次检查目标 ID、保护状态、任务是否仍可执行及停止权限。同步 hook 期间到达的用户输入也必须纳入复核。

Agent 插话不等于用户插话：它不保护 turn，也不能插进受保护的 turn。显式追加使用独立的 `append_instruction(target_turn_id=...)`：仅对该目标有效；已结束、停止、切换或不能接收追加的目标返回失效，不排入后来 turn。系统对当前工作的控制通知与普通 Agent 投递分开。

### 规范伪代码

```text
投递可执行Prompt(B, prompt):
    在同一次逻辑状态转换中:
        当前 = B.有效当前Turn
        if 当前为空且不存在尚未隔离的旧后端:
            开始新Turn(prompt, protected = 来自用户)
        else if 来自用户:
            立即设置处理时当前Turn的 protected
            插入该turn，或在绑定/停止确认期间持久化为其后继输入
        else if 未请求抢占 或 当前受保护 或 目标ID不符:
            加入待办队列
        else if 无权整体停止当前工作 或 会撤销自身祖先:
            加入待办队列，不取消任何部分
        else:
            提交旧工作停止决定；冻结其权限
            将这次投递指定为第一后继
            后端确认停止/隔离后，直接开启这次投递的新turn
```

用户插话先提交时，旧 turn 受保护，随后抢占排队。抢占先提交时，用户新输入归入抢占后的工作；停止确认期间先保存，不能重新保护并复活旧工作。明确回复旧 turn 的操作必须携带目标 ID，失效就返回失效。

## 3. 停止、恢复队列与正常结束

### 用户停止

用户停止针对 Agent 的已接受工作快照，包括当前执行、排队/blocked 任务、待执行 jobs、未读指令与属于停止范围的订阅。决定先持久化、递增停止代次，再异步取消后端。

用户停止不将旧未读指令恢复到下一 turn。已有结果与事实可保留为新的被动历史投递，但不能因此唤醒并恢复取消工作。停止之后新接受的用户请求属于新工作。

### Agent 显式停止、级联与抢占

模型使用 `cancel_task(task_id)` 取消其有权停止的业务任务。运行时沿任务实际归属生成各执行方的具体 turn ID，并以 ID 校验 `halt` 和停止确认。任务 ID 不等于“停止该 Agent 的所有工作”；不能因旧任务结束或迟到事件而取消新 turn。

保护限制抢占，不禁止合法显式停止。若取消范围只覆盖当前 turn 的一部分任务，其余任务继续，运行时告知哪些工作已撤销；不得为了方便把共享 turn 中的无关工作一起停掉。

普通未读输入在非用户停止时从旧 turn 移除，按原插话顺序整批恢复到旧待办之前，即使旧待办原本为空。抢占成功时优先级为：**抢占者 → 恢复的普通未读输入 → 原待办**。

停止已经完成的根任务仍遍历其下游，并以 `cascadeStopped` 记录剩余作用域已撤销，保留该根原有的终态和结果。

绑定旧 turn 的显式追加不恢复为普通待办，其目标结束就失效。否则它会从“修改特定工作”变成“开启不相关新工作”，违背操作语义。

队头弹出后直接开新 turn，不能再次走普通投递并误插到另一个 turn。正常结束也按同一调度顺序接续；存在后端仍持有的输入时，运行时等待其真实插入/取消结果，不能另发副本。

### 报告与任务完成

执行方的 turn 结束通常隐式完成任务；仍有要返回的子任务、job、订阅或未满足的产物契约时，业务任务继续开放。`report_result` 可以提前或明确报告失败，但不能声称未验证的工作已完成。

停止原因进入任务账本并按通知规则报告。主动停止者已经从工具应答得到确认，不再用第二条唤醒消息重复通知；其他应被告知的发起方收到对应结果。模型不得为了补通知而重复提交 `report_result`，也不得把停止任务重建成新任务以绕过停止。

## 4. “LM 已读取”、迟到事件与上下文恢复

xSB 使用可观察的**插入回执**作为运行时边界：ACP `session/prompt` 确认插入，或带明确 messageId 关联的后端回显；匿名回显只记录其执行位置，收到原请求响应后再按 native messageId 关联。所有投递统一使用 `session/prompt`，不再调用 `_session/steering`。写入 stdio、排入后端队列和出现 running 状态都不等于模型已经读取。

“已接收”表示 Hub 已持久化保存；“已插入”表示 Agent 后端会话接收，不证明模型请求已经发出或模型已经处理，控制命令也可能不调用模型。原生插入证据与随后确认的 Hub 消息关联后，历史投影按实际插入位置整理；不按回显的 FIFO 顺序猜测。选择更强的回执边界，避免把只是送进管道的指令当作已消费并丢掉。

每条输入由稳定 messageId 标识。在途输入仍归旧 turn 管理，收到取消/插入结果前不能同时恢复为可执行队列项。恢复时先移除旧归属，再转入后继归属；已有插入回执不能被更新上下文撤销。

重启时，后端已经收进对话的输入（账本为 inserted、seen 或 inserted_unprocessed）不再路由：续接的后端会话里已经有它，再发一次会让模型读两遍、可能执行两遍。它在原地结算，所载任务按“执行结果未知”失败，不重放；对话记录写一条失败说明，告诉用户这一轮在 xSB 停止时被打断、需要核对结果。重启前尚未确认的输入也不重新路由：统一按发送中断结算，保留原文和删除线，由用户显式重新发送。标准 prompt 携带稳定 messageId 作为 idempotencyKey，已核对的官方适配器可按原生会话保留的消息身份去重；不以重试创建第二份输入。

写入后端之前，Hub 先把“已提交给哪个后端会话”持久化到账本（`offered`）。此后只有三种结局：收到插入回执（inserted）；后端明确答复未插入（-32800，清除 `offered`，输入可以再次投递）；连接断开或断电，既没有回执也没有拒收。第三种记为 `insertion_uncertain`：原文和状态保留，所载任务按“插入未确认”失败，界面标“发送中断”，Hub 不自动重发，由用户核对后显式重新发送。它不等于“模型未看到”，也不等于“已插入”；之后若出现真实的插入证据，仍可升级为 inserted。

中枢停止期间（Hub.shutdown 起）不开始任何 turn、不启动任何后端进程：后端退出引起的 turn 结束不再接续下一条，排队的输入先保留到收件箱；下次启动统一结算旧未确认输入，不自动执行。

重启路由、延迟投递及出队都必须尊重终态：已丢弃输入、已经结束任务的残留委派邮件只结算并移除，不重新投递执行。若输入已被丢弃而任务尚未终结，运行时记录失败结果，不能让它脱离输入状态继续运行。

有效 turn ID、backendSessionId/上下文代次和工具 bridge token 共同隔离旧执行。停止确认与必要回执仅用于结算旧工作；旧结果不得覆盖新 turn 的状态或重新取得工具权限。隔离旧后端后才开启新执行。

普通 ACP 后端不一定提供 turn 标签。若停止后继续复用同一未标记连接，旧工具请求在新 turn 开始后才抵达时不能单靠正文辨别归属。因此，后端须在 initialize 中明确声明 `_meta["dev.xsb/turn-isolation"] = { version: 1, afterIdle: true }`，保证取消后的 idle 之前已结算/隔离全部旧工具调用与回复，才允许正常停止后复用原连接和完整上下文。

未声明该保证的后端，停止结算后撤销旧 bridge token、关闭旧进程，再用保存的 backendSessionId 在新进程恢复会话；恢复失败则写上下文未恢复边界，不从旧用户历史重建输入。这样旧请求在下一 turn 开始后也无法获权。此声明是协议实现的真实保证，不能仅为性能而虚报。停止确认最多等待 10 秒，超时强制隔离；只有已隔离后才能接续。定向追加在正常结束时仍未被读取、且已经发给后端，同样要隔离旧执行；中枢扣住、从未发出的追加只需失效，不重建后端会话。正常结束（后端在全部工具调用返回后才报告结束）没有迟到的旧请求，保留原进程与后端会话，以免无谓地让提示词缓存失效。

turn 因非取消原因失败时，已发出但没有插入回执的输入可能仍在后端里。它会被重新投递，所以先取消旧工作；未声明 turn-isolation 的后端同样撤销旧 bridge、在新进程里恢复会话，保证只有一份副本到达模型。

请求前缀（未声明 systemPrompt 时的常驻指令、交接、工作流上下文）随请求一起发出，拿到插入回执才算用掉；请求未被收进时，常驻指令和交接还给下一个请求，本轮的工作流上下文不还（下一轮会重新生成最新的一份）。交接待投递标记同样只在插入后清除。

上下文恢复是同一业务任务的有限尝试。未观察到执行的明确拒绝可以安全恢复；已有工具、权限请求或正常输出的输入不自动重放。取消代次、队列优先级、任务依赖和目标追加约束在恢复期间同样适用。

### 用户输入记录与送达状态

用户的每条输入在记录里恰好处于三态之一，只由插入回执推进，任何时候都不从记录中删除：

- **待送达**：中枢接收即写 `dev.xsb/accepted` 记录（与消息同一 messageId）。重启后从记录里仍能看到它在等待。
- **已送达**：插入回执后写 `user_message_chunk`，同一 id 取代待送达。模型收到的与原文不同时（图片看不到、超长存为文件、附加作用域说明），附 `dev.xsb/delivered`。
- **已终结**：写 `dev.xsb/discarded`，带原因（`stopped`、`failed`、`too_large`、`refused`、`expired`、`abandoned`）。会话层的丢弃、用户停止撤回、投递层否决与过期、退出时放弃、重启后结算，都走这一条记录；账本的 `message.discarded` 钩子为会话层没有记过的用户消息补写，按 id 只写一次。

**不自动补交。** 失败、取消和重启后未确认输入都不加入欠交清单，也不通过后续 prompt 或交接摘要重放。用户可以显式重新发送，使用新 messageId。旧数据的 owed 字段只作兼容读取，不注入新请求。

**幂等。** messageId 由客户端生成，并在中枢接收前一直保留（桌面端的发件箱 `.xsb2/desktop/outbox.json`）。中枢按 id 去重：已插入就直接应答，在途就等待原来那一份的回执，已丢弃就返回该状态，从不投第二份。`_dev.xsb/messages/status` 按 id 返回账本状态，`unknown` 表示中枢从未收到，客户端可以用原 id 再发。用户对已终结的消息"重新发送"时，用新 id 并带 `resendOf`：中枢记 `resentAs`；不再自动补交，明确重发可能导致模型收到重复内容。后端已经收进、但回执尚未落盘时中枢崩溃，重启将原输入标为发送中断，不自动再投；用户显式重发可能重复输入，这是产品接受的取舍。

**关闭与重启。** 中枢关闭期间，还没交给后端的输入留在收件箱，不记为未看到，下次启动结算为发送中断，不再自动投递。工作流重启只扣留节点会话的邮件和主会话中属于该工作流插话的邮件；已插入或已丢弃的，一律交给 `kernel.resume` 统一结算（写说明，任务按结果未知失败）。

关键决策征询偏好仅控制可选的意见询问频率，不改变权限审批、turn 归属、输入消费或停止权限。xSB ask 在工具调用中一直等待用户明确提交或跳过，不自动超时或选择默认答案；答案校验问题 ID、turn 和后端绑定后保护当前 turn，通过原工具结果返回，不产生后续 prompt。停止、结束、重绑、MCP 取消或断线、重启使问题失效，迟到定向回答不得转为待办。等待问题时不得执行依赖答案的工作，沉默不构成同意。设置更新沿用空闲时刷新后端绑定的机制，不抢占当前 turn。

## 5. 两次归纳证明

### 5.1 按事件数归纳

定义处理完前 n 个线性化事件后的不变量 P(n)：

1. 每个 Agent 至多一个具有执行资格的当前 turn。
2. 每条已接受输入只有一个逻辑归属：当前 turn（含其在途输入）、待办或终态。
3. 受保护的 turn 不因抢占而停止。

这里的“待办”包含未执行的 inbox、queued/blocked 工作以及已恢复但尚未启动的输入。Mailbox 持久化记录、队列对象和 turn 引用是同一输入的记录/索引，不被算作多个执行归属。

**基础情况：** 空闲、空队列，P(0) 成立。

**归纳步骤：** 假设 P(n) 成立。授权与依赖检查后，投递按表格进入互斥分支：空闲新建、用户插话并保护、排队或合法抢占。抢占提交前再次校验保护、目标及完整停止范围；新执行只在旧执行失去资格并完成隔离后开始。停止/正常结束先结算旧归属，再直接开始后继。未读输入先移除旧归属再恢复；用户停止则终结旧待办。迟到回执不能给新绑定落地，迟到模型结果不能控制新工作。因此 P(n+1) 成立。

异步绑定、停止确认与安全恢复是附加事件，保持串行执行资格和唯一输入归属；不是第二个可并发工作的 turn。由归纳得到有限事件序列上的状态安全。

### 5.2 按调用路径长度归纳

实际调用图的节点是通过 `dispatch_task`/`start_job` 登记的 taskId，边由运行时记录 `parents`。合法创建只连接到已存在的任务，因此形成 DAG；可信 hook 也必须保持这一约束。遍历按任务 ID 去重。未登记的外部进程不属于该证明的传播范围，模型不得绕过 Hub 私自建立隐藏委派或后台工作。

单边规则：处理一个停止根时，沿实际起因边判定子任务；中间节点已完成、失败或取消也不能阻止遍历。仍运行且仅由停止范围支撑的任务停止，排队子任务撤销待办；共享节点的停止资格按所有仍有效的支撑者判定。

**基础情况：** 一条起因边 A→B，遍历 A 会访问 B。

**归纳步骤：** 假设长度 k 的路径能访问末端。长度 k+1 的路径先访问第 k 层；该层无论自身是否结束都继续枚举调用边，故访问最后一层。由此任意深度的可达后代都会被判定，不依赖每个中间 Agent 再发生一次停止事件。

“共享时保留”影响取消资格，不影响访问可达性。汇合节点访问一次，联合停止多个根时先计算整个停止集合；不能逐根提前释放依赖，使共享子任务错误放行或漏停。

**并发前提：** 停止提交与新子任务挂接存在确定顺序。先提交的边纳入传播；停止已提交后，新增任务/job 与授权等待后返回的挂接必须拒绝。创建 hook 返回后和持久化前都要复核，不能只在函数入口检查。MCP `tools/call` 入口要求已启动且仍有效的当前 turn；有连接但处于 idle、绑定准备或停止状态时不能发起工具工作，工具 schema 查询不受此限制。

## 7. 后端运行与回合外输出

会话维护当前 run 及其 `turnId`（无主时为 `null`），不再用 `backendIdle/ranSince` 代替执行归属。只有属于当前 turn 的 run 结束才结束该 turn；无主 run 的 idle 不能结束仍在等 prompt 回执的 turn，也不能确认任务停止。回合已有 run 结束时仍等在途 prompt 的真实回执；后端把后续 prompt 插入自己的下一段执行时，仍由同一逻辑 turn 认领。已结束 run 的迟到输出保持结束状态。

内核提供三个 hook：`acp.run_started`、`acp.run_ended` 是观察点；`acp.pre_unowned_run` 是决策点，默认 `action: show`，扩展可改为 `stop`。决策否决或抛错按 fail-closed 请求后端取消；提交前复核 run 仍是原来的无主运行。插入认领时用同一 run ID 再发 `run_started`，表示归属变化，历史输出不改写。

每条后端输出附 `_meta["dev.xsb/run"] = { id, turnId, state }`；开始、认领与结束另写 `session_info_update`，结束带 `stopReason` 和后端的 `_claude/origin`（如果有）。边界与归属进入 transcript，历史查询和实时转发采用同样的数据。无主输出不推进输入消费、不成为任务交付、不授予 MCP 或工具权限。

桌面按 run ID 和当时的 owner 分段；回合外段带“回合外”标题与结束说明，收到该 run 的 idle 后关闭所有分段的流式光标。文字、思考与工具更新只显示，不改变智能体状态、输入栏或停止目标。用户停止仍只针对 turn 及已接受的工作，不因展示回合外输出而扩大取消范围。后端自带的后台完成通知可以显示；允许使用后端原生后台命令；不得绕过中枢建立隐藏委派。

验证：`turns.test.ts` 覆盖无回合运行、pending prompt、插入认领、idle 先于回执、停止/veto 策略和权限隔离；`stop.test.ts` 验证回合外结束不能确认 turn 停止；`kernel.test.ts` 验证默认策略和 hook 的 fail-closed；ACP 端到端与桌面测试验证后台完成通知、实时与历史边界，以及分段收尾。

## 8. 输入投递与队首控制（2026-11-26）

用户输入即保护 turn。输入投递使用 ACP v2 session/prompt，每会话至多一个等待插入回执的批次；后续用户插话在当前 turn 扣留，回执到达即接续，不等待整个 turn 结束。绑定、恢复和停止隔离仍是执行前提。运行状态、输出和正常结束均不能推进输入确认。

Hub 原文、接收账本与历史，插入确认与历史，取消与队列撤回分别在同一 WAL 事务提交；客户端确认在持久提交后发送。普通 Agent 调用结果不自动回传 prompt。

插件可向所属主对话发布带来源的 Markdown。Hub 将正文持久化后通知客户端，历史回放也读取该记录。这条记录不进入收件箱，不创建、插入或结束 turn，不计入模型历史或交接预算。工作流插件用该入口展示终点结果，需要主 Agent 决策的控制通知仍使用正常投递。

排队输入均可取消；只有队首显示立即发送。用户授权该条加入当前 turn 并保护它，提交点校验队首 ID、目标 turn、DAG 依赖及停止状态。在途队首保留占位至真实回执或明确终结，后续项不能越序。已提交给执行器的输入不能作为队列项撤回。

重启前未确认输入不重投，blocked 任务也结算，避免失败释放依赖后重新执行旧输入。收到回执仅确认执行器会话插入，不保证上下文持久化或实际 LM 请求包含。界面使用等待发送、发送中、排队中、已送达、已取消、发送失败和发送中断，终结输入保留删除线。执行器原会话恢复失败只记录上下文边界，不从旧 Hub 历史重建消息。见 [完整方案](INPUT-DELIVERY.md)。
