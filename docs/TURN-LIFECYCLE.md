# 多 Agent 任务与 turn 生命周期契约

2026-11-21。规范状态：运行时契约；模型会话说明包含必须遵守的摘要。

## 1. 核对结论与证明边界

按事件数归纳证明状态转移安全、按调用路径长度归纳证明停止传播可达，方法成立。xSB 采用这两组不变量约束任务开启和结束，运行时负责强制执行，模型负责使用正确的工具与诚实报告结果。

应用证明时必须明确定义：

- **turn 与 task 不同。** turn 是一次串行模型执行及其输入；task 是持久化的业务任务。task 可以等待多个 turn，也可以在 turn 尚未退出时通过 `report_result` 结束。一个 turn 可以承接多个仍开放的任务。
- **投递表针对已获授权、依赖已满足且需要执行的 prompt。** `lazy` 邮件留在 inbox；`after` 未满足的 task 留在 blocked；它们属于待办，不因接收请求就立刻开 turn。
- **抢占权限是前提。** `dispatch` 权限不等于任意停止其他发起方的工作。混合所有者的 turn 若无法整体合法停止，抢占请求整体排队，不先取消一部分。请求也不能通过停止祖先把自身工作撤掉。
- **传播可达不等于所有后代都要取消。** 内置 `spare` 策略下每个实际调用后代都参与判定；只为停止范围而存在的后代取消，仍被无关活任务支撑的共享后代保留。`after` 是次序边，不能当成调用/取消边。可信扩展若显式采用 `force`，属于另一个传播策略，须单独说明授权与证明，不能声称满足这里的共享保留规则。
- **逻辑失效与后端退出分开。** 停止决定先持久化并冻结执行权限；后端确认 idle 或被隔离后才启动后继。停止确认期间可以没有有效执行 turn，不能同时启动两个后端工作。

这些约束将简化伪代码细化为实际产品语义。归纳证明覆盖状态安全、输入归属和传播覆盖；模型能否正确完成任务、外部程序能否及时返回、外部写入是否只执行一次，还需要独立的执行与恢复约束。

## 2. 开启与投递规则

插话归入处理时的当前 turn；抢占撤销旧执行资格，并使这次投递优先开启新 turn；排队项从队头取出后直接成为新 turn 的输入。

| B 状态 | 投递方 | 请求抢占 | 行为 |
| --- | --- | --- | --- |
| 空闲 | 任意 | 任意 | 开新 turn；用户输入使其受保护 |
| 有 turn | 用户 | 任意 | 插话；接收时立即保护当前 turn |
| 有受保护 turn | Agent | 任意 | 排队 |
| 有未受保护 turn | Agent | 否 | 排队 |
| 有未受保护 turn | Agent | 是 | 目标 ID、权限及整体停止范围校验通过后抢占；否则排队 |

**保护状态属于当前 turn。** 不能用初始发起方替代 `turn.protected`。Agent 发起的 turn 收到用户插话后仍是同一个 turn，但立即受保护，保护不等模型读取后才生效。

上下文恢复期间即使工具调用被暂停，用户插话仍归当前逻辑 turn，并立即保护它。绑定或恢复完成前已收到的用户纠正合并进首个模型请求，不能先执行旧指令再补交已知约束。

抢占使用 `dispatch_task(onBusy="replace", target_turn_id=...)`。模型通过 `list_agents` 获取快照，运行时在提交停止决定前再次检查目标 ID、保护状态、任务是否仍可执行及停止权限。同步 hook 期间到达的用户输入也必须纳入复核。

普通 Agent 发送任务、消息或结果不能冒充用户插话。显式追加使用独立的 `append_instruction(target_turn_id=...)`：仅对该目标有效；已结束、停止、切换或不能接收追加的目标返回失效，不排入后来 turn。系统对当前工作的控制通知与普通 Agent 投递分开。

### 规范伪代码

```text
投递可执行Prompt(B, prompt):
    在同一次逻辑状态转换中:
        当前 = B.有效当前Turn
        if 当前为空且不存在尚未隔离的旧后端:
            开始新Turn(prompt, protected = 来自用户)
        else if 来自用户:
            立即设置处理时当前Turn的 protected
            插入该turn，或在绑定/停止确认期间持久化为其后继输入
        else if 未请求抢占 或 当前受保护 或 目标ID不符:
            加入待办队列
        else if 无权整体停止当前工作 或 会撤销自身祖先:
            加入待办队列，不取消任何部分
        else:
            提交旧工作停止决定；冻结其权限
            将这次投递指定为第一后继
            后端确认停止/隔离后，直接开启这次投递的新turn
```

用户插话先提交时，旧 turn 受保护，随后抢占排队。抢占先提交时，用户新输入归入抢占后的工作；停止确认期间先保存，不能重新保护并复活旧工作。明确回复旧 turn 的操作必须携带目标 ID，失效就返回失效。

## 3. 停止、恢复队列与正常结束

### 用户停止

用户停止针对 Agent 的已接受工作快照，包括当前执行、排队/blocked 任务、待执行 jobs、未读指令与属于停止范围的订阅。决定先持久化、递增停止代次，再异步取消后端。

用户停止不将旧未读指令恢复到下一 turn。已有结果与事实可保留为新的被动历史投递，但不能因此唤醒并恢复取消工作。停止之后新接受的用户请求属于新工作。

### Agent 显式停止、级联与抢占

模型使用 `cancel_task(task_id)` 取消其有权停止的业务任务。运行时沿任务实际归属生成各执行方的具体 turn ID，并以 ID 校验 `halt` 和停止确认。任务 ID 不等于“停止该 Agent 的所有工作”；不能因旧任务结束或迟到事件而取消新 turn。

保护限制抢占，不禁止合法显式停止。若取消范围只覆盖当前 turn 的一部分任务，其余任务继续，运行时告知哪些工作已撤销；不得为了方便把共享 turn 中的无关工作一起停掉。

普通未读输入在非用户停止时从旧 turn 移除，按原插话顺序整批恢复到旧待办之前，即使旧待办原本为空。抢占成功时优先级为：**抢占者 → 恢复的普通未读输入 → 原待办**。

停止已经完成的根任务仍遍历其下游，并以 `cascadeStopped` 记录剩余作用域已撤销，保留该根原有的终态和结果。

绑定旧 turn 的显式追加不恢复为普通待办，其目标结束就失效。否则它会从“修改特定工作”变成“开启不相关新工作”，违背操作语义。

队头弹出后直接开新 turn，不能再次走普通投递并误插到另一个 turn。正常结束也按同一调度顺序接续；存在后端仍持有的输入时，运行时等待其真实插入/取消结果，不能另发副本。

### 报告与任务完成

执行方的 turn 结束通常隐式完成任务；仍有要返回的子任务、job、订阅或未满足的产物契约时，业务任务继续开放。`report_result` 可以提前或明确报告失败，但不能声称未验证的工作已完成。

停止原因进入任务账本并按通知规则报告。主动停止者已经从工具应答得到确认，不再用第二条唤醒消息重复通知；其他应被告知的发起方收到对应结果。模型不得为了补通知而重复提交 `report_result`，也不得把停止任务重建成新任务以绕过停止。

## 4. “LM 已读取”、迟到事件与上下文恢复

xSB 使用可观察的**插入回执**作为运行时边界：ACP `session/prompt` 确认插入，或后端回显被插入的输入；`_session/steering` 需回显。写入 stdio、排入后端队列和出现 running 状态都不等于模型已经读取。

“插入”是协议层保证，不是模型注意力或理解的证明。选择更强的回执边界，避免把只是送进管道的指令当作已消费并丢掉。

每条输入由稳定 messageId 标识。在途输入仍归旧 turn 管理，收到取消/插入结果前不能同时恢复为可执行队列项。恢复时先移除旧归属，再转入后继归属；已有插入回执不能被更新上下文撤销。

重启路由、延迟投递及出队都必须尊重终态：已丢弃输入、已经结束任务的残留委派邮件只结算并移除，不重新投递执行。若输入已被丢弃而任务尚未终结，运行时记录失败结果，不能让它脱离输入状态继续运行。

有效 turn ID、backendSessionId/上下文代次和工具 bridge token 共同隔离旧执行。停止确认与必要回执仅用于结算旧工作；旧结果不得覆盖新 turn 的状态或重新取得工具权限。隔离旧后端后才开启新执行。

普通 ACP 后端不一定提供 turn 标签。若停止后继续复用同一未标记连接，旧工具请求在新 turn 开始后才抵达时不能单靠正文辨别归属。因此，后端须在 initialize 中明确声明 `_meta["dev.xsb/turn-isolation"] = { version: 1, afterIdle: true }`，保证取消后的 idle 之前已结算/隔离全部旧工具调用与回复，才允许正常停止后复用原连接和完整上下文。

未声明该保证的后端，停止结算后撤销旧 bridge token、关闭旧进程，再用保存的 backendSessionId 在新进程恢复会话；恢复失败则采用带边界的交接。这样旧请求在下一 turn 开始后也无法获权。此声明是协议实现的真实保证，不能仅为性能而虚报。停止确认最多等待 10 秒，超时强制隔离；只有已隔离后才能接续。定向追加在正常结束时仍未被读取，同样要隔离旧执行。

上下文恢复是同一业务任务的有限尝试。未观察到执行的明确拒绝可以安全恢复；已有工具、权限请求或正常输出的输入不自动重放。取消代次、队列优先级、任务依赖和目标追加约束在恢复期间同样适用。

## 5. 两次归纳证明

### 5.1 按事件数归纳

定义处理完前 n 个线性化事件后的不变量 P(n)：

1. 每个 Agent 至多一个具有执行资格的当前 turn。
2. 每条已接受输入只有一个逻辑归属：当前 turn（含其在途输入）、待办或终态。
3. 受保护的 turn 不因抢占而停止。

这里的“待办”包含未执行的 inbox、queued/blocked 工作以及已恢复但尚未启动的输入。Mailbox 持久化记录、队列对象和 turn 引用是同一输入的记录/索引，不被算作多个执行归属。

**基础情况：** 空闲、空队列，P(0) 成立。

**归纳步骤：** 假设 P(n) 成立。授权与依赖检查后，投递按表格进入互斥分支：空闲新建、用户插话并保护、排队或合法抢占。抢占提交前再次校验保护、目标及完整停止范围；新执行只在旧执行失去资格并完成隔离后开始。停止/正常结束先结算旧归属，再直接开始后继。未读输入先移除旧归属再恢复；用户停止则终结旧待办。迟到回执不能给新绑定落地，迟到模型结果不能控制新工作。因此 P(n+1) 成立。

异步绑定、停止确认与安全恢复是附加事件，保持串行执行资格和唯一输入归属；不是第二个可并发工作的 turn。由归纳得到有限事件序列上的状态安全。

### 5.2 按调用路径长度归纳

实际调用图的节点是通过 `dispatch_task`/`start_job` 登记的 taskId，边由运行时记录 `parents`。合法创建只连接到已存在的任务，因此形成 DAG；可信 hook 也必须保持这一约束。遍历按任务 ID 去重。未登记的外部进程不属于该证明的传播范围，模型不得绕过 Hub 私自建立隐藏委派或后台工作。

单边规则：处理一个停止根时，沿实际起因边判定子任务；中间节点已完成、失败或取消也不能阻止遍历。仍运行且仅由停止范围支撑的任务停止，排队子任务撤销待办；共享节点的停止资格按所有仍有效的支撑者判定。

**基础情况：** 一条起因边 A→B，遍历 A 会访问 B。

**归纳步骤：** 假设长度 k 的路径能访问末端。长度 k+1 的路径先访问第 k 层；该层无论自身是否结束都继续枚举调用边，故访问最后一层。由此任意深度的可达后代都会被判定，不依赖每个中间 Agent 再发生一次停止事件。

“共享时保留”影响取消资格，不影响访问可达性。汇合节点访问一次，联合停止多个根时先计算整个停止集合；不能逐根提前释放依赖，使共享子任务错误放行或漏停。

**并发前提：** 停止提交与新子任务挂接存在确定顺序。先提交的边纳入传播；停止已提交后，新增任务/job 与授权等待后返回的挂接必须拒绝。创建 hook 返回后和持久化前都要复核，不能只在函数入口检查。MCP `tools/call` 入口要求已启动且仍有效的当前 turn；有连接但处于 idle、绑定准备或停止状态时不能发起工具工作，工具 schema 查询不受此限制。
