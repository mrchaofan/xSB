# 会话与工作流

每次新建会话都会创建一个主 Agent。工作区可以保存多个主会话，它们各自拥有对话历史、模型后端和工作流，Agent 使用工作区中的文件。询问、写作或单次创作直接在当前会话完成。需要并行工作、条件选择或多步交付时，主 Agent 才建图。

主对话可在左栏右键菜单中重命名；名称会持久保存，后端生成的标题不再覆盖用户设置的名称，正在执行时也可改名。

首次用户输入先提供一个短的临时名称，Claude 和 Codex 适配器生成的名称通过 `session_info_update.title` 接管；标题在 turn 结束后到达也立即广播到界面。自动名称去掉多余空白并限制为 64 字符，空标题和系统提示词标题不采用。新建时指定名称或手动重命名都受保护；任务 Agent 保持图中的节点名称。

## 状态查询与控制 API

`Workflows` 是 Hub 的工作流服务对象，封装状态、调度与持久化；`workflow-state.ts` 负责图求值及状态转换，`acp-server.ts` 只映射协议。查询和更新通知使用同一份快照，UI 不从节点标签自行推断允许的动作。相关插话的 turn 开始、结束或失败时，服务也发布新快照，因为控制动作还取决于有效执行是否存在。

| 对象 API | ACP 方法 | 语义 |
| --- | --- | --- |
| `get(sessionId)` | `_dev.xsb/workflow/get` | 查询单个主会话的状态，无执行副作用 |
| `list()` | `_dev.xsb/workflow/list` | 查询已登记工作流 |
| `stop(sessionId, version, node?)` | `_dev.xsb/workflow/stop` | 用户停止所示活动版本的全部任务，或按名称停止一个任务节点，返回新快照 |
| `control(sessionId, "pause" / "resume" / "rollback", nodes?)` | `_dev.xsb/workflow/pause` / `resume` / `rollback` | 校验当前作用域、提交状态、调度并返回新快照 |

快照包含 `state`（`empty`、`proposed`、`running`、`paused`、`completed`）、整体 `controls`（`stop`、`pause`、`resume`、Markdown 图的 `rollback`） 和各节点的 `controls`。候选及历史版本仍独立展示。正在处理的主会话插话不能被误显示为等待恢复；任务节点仍有工作、追加、选择或未完成插话时，不算整体完成。

工作流到达有效终点时，插件将终点交付和主对话中的 Markdown 结果在同一事务中持久化。主 Agent 即使正在处理另一件事，用户也能看到结果。整体状态 `completed` 还要求各节点、追加工作、插话与待投递的控制通知均已结清。完成后暂停或恢复返回同一终态，重启也保留该状态。未完成工作需要显式恢复。

## 规划与执行

DAG 的任务节点和结束节点使用系统提示词声明的对话语言，名称简短且说明职责；中文对话用中文名称，英文对话用英文名称。`node`、边端点和工具参数引用同一名称；同一职责的节点改图时保留已有名称，以沿用会话。

主 Agent 调用 `plan({graphJsonl})` 保存一个候选，替换之前的候选。候选供预览，现有活动图继续运行。不带参数调用 `execute({})` 采用本轮看到的候选，也可以调用 `execute({graphJsonl})` 直接采用完整图。版本名由宿主按会话顺序分配（`plan-1`、`plan-2`…），同一图定义始终得到同一版本名；模型不起名，也不传版本名，宿主按本轮实际展示过的候选核对。每个主会话最多有一个候选和一个活动版本，候选的规划依据发生变化后须重新规划。

主会话的 `[xSB workflow]` 上下文不是每轮都附：

- **上下文里没有图时附完整 JSONL**：首轮、后端压缩上下文之后（`compaction_update`，或用量回落）、换后端会话续接之后，附上活动图和候选图的完整 JSONL（与提交格式相同）。工作流结束后也一样。
- **模型自己得不到的变化立即附**：暂停、出错、用户停止丢掉的追加工作和通知。
- **工作流进行中每 10 轮附一次**（`WORKFLOW_REFRESH_TURNS`），只带状态和变化了的定义。需要主 Agent 处理节点上报或旧图分支邀请时，插件另发控制通知。
- **工作流结束后停止定期提醒**。终点结果以插件署名展示在主对话里，发布时主 Agent 不会收到 prompt，上下文交接也会跳过这条展示记录。

全文随时可凭 `graphRef` 用 `read_context` 读取。主对话的消息只交给主 Agent，任务 Agent 收不到；上下文里只有工作流的状态和交付摘要，没有任务 Agent 的对话。

### Markdown 图

主 Agent 用 JSONL 写节点和边，每行一个对象。任务节点用 `requirements` 声明接收几项参数、如何提供、要交付什么。真实的参数在 `input` 中传递，两者都用 Markdown。只有入度为零的入口任务能在图定义中写 `input`。节点还可以配置 `model` 和 `agent`，同一职责沿用已有会话和技能。[任务 Agent 配置与缓存](WORKFLOW-AGENT-CONFIG.md)

```jsonl
{"node":"提取角色","requirements":"需要剧本文字或文件链接，交付主要角色姓名和外观依据。","input":"剧本：[春潮](./春潮.md)"}
{"node":"整理画风","requirements":"需要画风文字，交付绘图时要遵守的风格与构图。","input":"黑白水墨，全身像。"}
{"node":"生成角色图","requirements":"需要角色清单和画风，按角色名交付设定图文件链接。"}
{"node":"交付角色图","kind":"end"}
{"from":"提取角色","to":"生成角色图"}
{"from":"整理画风","to":"生成角色图"}
{"from":"生成角色图","to":"交付角色图"}
```

两个入口可以并行执行。任务 Agent 调用 `finish({output})` 将实际交付存入自己的节点。执行正常结束且指派仍有效时，Hub 接纳交付。「生成角色图」等两个前驱都交付后，才读取两份 `output`，按图中稳定的顺序以来源节点名分段，作为本次指派的 `input`。只有一个生效的直接前驱时，接收其完整原文。终点按相同规则读取交付，把正文发布到主对话。

条件边的 `case` 是文字，例如 `{"from":"整理需求","to":"规划跨城路线","case":"游览两座或更多城市"}`。来源任务 Agent 对照自己提交的正文及 `finish` 返回的候选，调用 `choose({"node":"规划跨城路线"})`。Hub 从当前指派确定起点，把选中的目标写入来源节点的 `choice`。普通边只需已接纳的产物即可放行，条件边还需相应的选择。跳过的边不提供材料。若全部条件入边跳过，或所有入边均跳过，节点也跳过。每种合法选路都到达一个有效终点。

### 暂停、回退和修改

暂停保存本次执行已经提交的正文和选择。恢复时，如果只差选路，原任务 Agent 从保存的正文和候选继续选择。它们均已提交时，Hub 核对当前指派并接纳正常结束的执行。待汇合节点在入边状态确定后才取得输入。

主 Agent 可用 `rollback({nodes:["整理需求"]})` 从指定任务回退，用 `rollback({})` 回退全图。用户在主对话里说明需要重做的内容，主 Agent 根据依赖和已有交付选择回退范围。Hub 清除回退范围内的当前交付、选择和指派输入，撤回依赖它们的派发和当前终点结果。独立前驱的交付可继续使用。回退前的状态可从历史下拉查看。

用 `execute({replaceNode})` 提交单个任务的完整定义。修改依赖或节点集合时提交完整图。改图使指派依据失效时，下游重新等待；保留独立任务的交付。主 Agent 用 `prompt({node,text})` 派独立追加工作，追加记录保存在节点，数据边只读取正式图任务的交付。工具收据支持幂等重投。

### 既有工作流

已有摘要图和使用 `inputSchema`、`schema`、`bind` 的图按原有定义、工具参数和在途指派继续运行。它们使用 `finish({summary,result?})` 交付，主 Agent 根据选路邀请调用 `choose({from,cases})`，仍支持旧图的多选。契约图按 JSON Pointer 绑定、校验命名输入及实际结果，终点发布命名输入。较早的摘要图终点列出参与交付。桌面可以分别查看这些历史版本的输入、交付和来源。

工作流工具的参数、收据、返回值，以及实际送达模型的工作流上下文和作用域说明，单独记录在项目的 `.xsb2/agents/<agentId>/workflow/<sessionId>.jsonl` 中。记录包含格式版本、来源、时间、会话和 turn ID。插件读取旧审计数据时也识别原对话日志里的 `dev.xsb/workflow-log`，无需改写既有对话。

## 内置工具的感知

工作流服务注册 MCP 工具，以及一段随会话语言提供的简短说明。用户直接描述目标即可。涉及多份相互依赖的交付、并行准备或条件分支时，主 Agent 主动用 `workflow.plan` 保存候选图。简单请求直接回答。用户要求审阅时，先展示候选并等待确认。需要建图格式和完整示例时，主 Agent 可以读取 `workflow.guide()`。活动图与候选图仍从当前会话的真实状态恢复。向用户征询决定时，Agent 使用后端原生提问工具。[向用户提问](ASK.md)

服务派发的指派和通知在 Hub 内部标记提供者。出队及向 ACP 提交前，Hub 按消息 ID 向提供者校验有效性。已发送的输入按真实插入回执结算。工作流视图独立读取图快照，主对话通过带来源的 Markdown 记录显示交付和撤回。

## 用户直接问任务 Agent

用户可以在任务会话里随时提问。任务 Agent 先给问题归类，再处理：

1. **和自己的任务有关**（目标、输入、素材、进度、交付）：自己处理。如果任务本身需要改变（交付内容、超出给定的输入或范围），调用 `escalate({message, pauseSelf: true})`，节点暂停，等主 Agent 决定，不悄悄改方向；当前交付需要作废时再加 `invalidateSelf`。
2. **和自己的任务无关，但和整体任务有关**（其他节点、计划、顺序、优先级、最终结果）：不自己处理，也不替主 Agent 回答。调用 `escalate({message})`，附上用户原话；节点照常工作。
3. **和两者都无关**：直接简短回答，不改动任何工作。

上报之后，任务 Agent 告诉用户主 Agent 会在主对话里处理。拿不准是第 1 类还是第 2 类时就上报，只有自己的任务必须改变时才暂停。

上报只有一个工具 `escalate`，两种情形的区别只在节点要不要停下来等。主会话收到通知 `{escalate, message, userSaid?, paused, invalidateSelf?}` 后，在主对话里回答用户，需要时用 `execute`（`replaceNode`）、`prompt`、`pause` 或 `resume` 调整工作流。`paused` 为真表示节点在等主 Agent：用 `execute({replaceNode})` 采用修改后的定义，或用 `resume({nodes:[该节点]})` 维持原任务。

## 任务 Agent 向用户提问

任务 Agent 需要用户决定才能完成本次指派时，使用 Claude 或 Codex 的原生同步提问。答复通过原 ACP 请求返回，当前 attempt 继续执行并在同一轮调用 `finish`。支持异步提问的 Codex 模型也可以先开展与答案无关的工作。任务节点的执行轮结束、暂停、停止或后端换绑时，仍待答的表单关闭，迟到的答复失效。[向用户提问](ASK.md)

## 插话、暂停与恢复

桌面工作流面板提供「停止工作流」和「停止任务」。Hub 先校验活动版本，将图或节点的暂停与对应任务会话的停止一并提交，撤销该范围内的旧待办和排队追加，再取消后端执行。尚未派发的任务节点也可以停止。停止节点后，依赖它的工作等待，独立分支继续。停止全图保留主会话，用户可继续交谈并要求主 Agent 恢复执行。

主会话可以直接回答无关问题。工作流进行中，桌面主输入框发出的消息针对当前工作流：模型收到时前面附一句说明，处理这条插话期间暂缓图的派发和接纳。工作流结束后，主对话的消息就是普通消息，不再附说明。任务会话默认针对当前工作或交付，选“仅询问历史”可单独讨论旧版本。工作流的 `pause` 和 `resume` 可传 `nodes` 指定范围。任务需要改向时调用 `escalate({message, pauseSelf: true, invalidateSelf?})`，主 Agent 采用修改，或用 `resume({nodes:[…]})` 沿用原目标。多个暂停来源分别生效。

插话只有进入模型的对话才生效：没有送达的插话（被拒、失败、过期）不挡住图，恢复时也不续做。已送达的插话所在那一轮失败或被停止后，视图会标出 `interrupted`，用户可在主对话要求主 Agent 继续。用户停止清掉的追加工作和未送达的通知，会随下一份工作流上下文告诉主 Agent。正在执行的指派被改图撤销后，节点的下一份指派会写明旧的已作废；节点会话换了上下文后，续做时重新发送整份指派。通知没有送达时会自动重投，最多 3 次。

宿主重启时为未完成工作增加全图暂停，期间仍可查看图和历史。明确恢复后，已结束的待接纳交付重新校验，执行中断的工作在原会话续做。升级时，旧版仍待投递且可核实的终点通知按原交付 ID 发布一次。已确认插入模型的旧通知沿用原有历史。

## 文件

桌面「文件」面板列出当前主会话和它的工作流节点通过后端工具生成或修改的本地文件。Hub 从 ACP v2 的 `tool_call_update` 读取结构化 `diff.changes`，按 `toolCallId` 合并分段更新，在工具成功后采用变更。同一路径只显示一项，移动会更新路径，删除会将路径移出列表。

Claude 的 `NotebookEdit` 和向空文件写入内容的 `Edit` 有时只提供工具名和结构化输入路径，此时按成功调用的目标收录。Codex 生图结果带有已保存的本地路径时也会显示。工具只上报命令、读取位置或内联图片时，无法据此确认生成了哪个文件。

Markdown 节点通过 `finish({output})` 交付本地文件链接时，「文件」也会收录链接指向的现有文件，包括追加交付和保存在工作流历史版本中的交付。列表从会话事件和工作流交付重建，同一路径只显示一次。文件直接从原位置打开，旧版登记过的文件保留在磁盘原处。

## 输入与追加工作结果（2026-11-26）

输入接收与历史记录持久提交后投递，每会话一批在途 prompt 等待 ACP 插入回执。用户插话接收即保护 turn，回执到达即可续发，不等待整个 turn 结束。排队输入支持取消和仅队首的立即发送；立即发送由用户授权并保护当前 turn，在途队首占位直到确认或明确终结。

普通 Agent 调用不默认回传结果 prompt。追加工作完成后保存到节点 `additionalResults`，节点视图提供结果摘要。DAG 终点通过插件发布主对话正文。Markdown 图的选路归来源任务 Agent。升级与旧图的分支邀请投递给主 Agent。

重启前未确认输入终结且不补发；不得恢复原邮件、加入欠交清单或将原文再次注入。明确 resume 可以继续保存的工作流 assignment；已接收用户插话的继续请求只引用原消息 ID，如果上下文已经缺失要求用户重新发送，不复制原文。

节点首次接到指派，任务聊天显示「开始 节点名」。Hub 将任务要求和本次输入放在同一个 ACP v2 请求的补充文本块中，标记 `annotations.audience: ["assistant"]`。追加、恢复和选路续做也各有简短标题。模型同时获得执行所需的上游交付、候选或撤回说明。实时聊天和历史回放只显示公开内容，用户在同一轮补发的文字按原样展示。图中保留结构化的输入与交付供查看。
