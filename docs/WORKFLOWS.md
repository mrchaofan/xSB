# 会话与工作流

每次新建会话都会创建一个主 Agent。工作区可以保存多个主会话，它们各自拥有对话历史、模型后端和工作流，工作区共享同一份资产登记。询问、写作或单次创作直接在当前会话完成。需要并行工作、条件选择或多步交付时，主 Agent 才建图。

主对话可在左栏右键菜单中重命名；名称会持久保存，后端生成的标题不再覆盖用户设置的名称，正在执行时也可改名。

首次用户输入先提供一个短的临时名称，Claude 和 Codex 适配器生成的名称通过 `session_info_update.title` 接管；标题在 turn 结束后到达也立即广播到界面。自动名称去掉多余空白并限制为 64 字符，空标题和系统提示词标题不采用。新建时指定名称或手动重命名都受保护；任务 Agent 保持图中的节点名称。

## 状态查询与控制 API

`Workflows` 是 Hub 的工作流服务对象，封装状态、调度与持久化；`workflow-state.ts` 负责图求值及状态转换，`acp-server.ts` 只映射协议。查询和更新通知使用同一份快照，UI 不从节点标签自行推断允许的动作。相关插话的 turn 开始、结束或失败时，服务也发布新快照，因为控制动作还取决于有效执行是否存在。

| 对象 API | ACP 方法 | 语义 |
| --- | --- | --- |
| `get(sessionId)` | `_dev.xsb/workflow/get` | 查询单个主会话的状态，无执行副作用 |
| `list()` | `_dev.xsb/workflow/list` | 查询已登记工作流 |
| `control(sessionId, "pause" / "resume", nodes?)` | `_dev.xsb/workflow/pause` / `resume` | 校验当前作用域、提交状态、调度并返回新快照 |

快照包含 `state`（`empty`、`proposed`、`running`、`paused`、`completed`）、整体 `controls: {pause,resume}` 和各节点的 `controls`。候选及历史版本仍独立展示。正在处理的主会话插话不能被误显示为等待恢复；任务节点仍有工作、追加、选择或未完成插话时，不算整体完成。

`completed` 要求到达有效终点、没有未完成工作或插话，且持久化结果通知已送达。节点已交付但通知还在队列时，仍可暂停或恢复通知投递。完成后的暂停/恢复请求幂等返回终态，不重建任务，不重投已确认的通知。完成图重启后保持完成；未完成工作显式恢复。用于减少模型上下文注入的 `settled` 判断另可在等待终点通知时成立，因为图本身已无任务或选择待执行。

## 规划与执行

DAG 的任务节点和结束节点使用系统提示词声明的对话语言，名称简短且说明职责；中文对话用中文名称，英文对话用英文名称。`node`、边端点和工具参数引用同一名称；同一职责的节点改图时保留已有名称，以沿用会话。

主 Agent 调用 `plan({graphJsonl})` 保存一个候选，替换之前的候选。候选供预览，现有活动图继续运行。不带参数调用 `execute({})` 采用本轮看到的候选，也可以调用 `execute({graphJsonl})` 直接采用完整图。版本名由宿主按会话顺序分配（`plan-1`、`plan-2`…，与资产版本 `v1` 区分），同一图定义始终得到同一版本名；模型不起名，也不传版本名，宿主按本轮实际展示过的候选核对。每个主会话最多有一个候选和一个活动版本，候选的规划依据发生变化后须重新规划。

主会话的 `[xSB workflow]` 上下文不是每轮都附：

- **上下文里没有图时附完整 JSONL**：首轮、后端压缩上下文之后（`compaction_update`，或用量回落）、换后端会话续接之后，附上活动图和候选图的完整 JSONL（与提交格式相同）。工作流结束后也一样。
- **模型自己得不到的变化立即附**：暂停、出错、用户停止丢掉的追加工作和通知。
- **工作流进行中每 10 轮附一次**（`WORKFLOW_REFRESH_TURNS`），只带状态和变化了的定义。节点完成、等待选择、上报都有各自的通知；采用、改图、追加是模型自己做的，它知道。
- **工作流结束后不再附**：到达终点，没有节点在工作、排队或等待选择，也没有候选。模型从对话历史里保持对它的感知。

全文随时可凭 `graphRef` 用 `read_context` 读取。主对话的消息只交给主 Agent，任务 Agent 收不到；上下文里只有工作流的状态和交付摘要，没有任务 Agent 的对话。

JSONL 中每个节点和每条边各占一行。任务节点支持 `input`、`model`、结果的 JSON Schema `schema`，以及固定的 `agent:{systemPrompt?,skills?:[{name,description,content}]}` 配置。主 Agent 为新职责生成简短角色和可复用的技能正文；同名同类型节点重用时，省略的角色和技能配置自动继承，显式改动被运行时拒绝。完整规则与 ACP 能力边界见 [任务 Agent 配置与缓存](WORKFLOW-AGENT-CONFIG.md)。下面的审片图通过后直接汇总，需要修订时先执行修图。

```jsonl
{"node":"绘制","prompt":"绘制并登记定妆图。"}
{"node":"审片","prompt":"审查本次定妆图。"}
{"node":"修图","prompt":"按审片意见修订定妆图。"}
{"node":"通过","kind":"end"}
{"node":"修订完成","kind":"end"}
{"from":"绘制","to":"审片"}
{"from":"审片","to":"通过","case":"pass"}
{"from":"审片","to":"修图","case":"revise"}
{"from":"修图","to":"修订完成"}
```

普通边等待有效交付。条件边还等待针对该次交付的选择。单选须选一个已有选项，多选源加 `"multi":true`，允许 `choose({from,cases:[]})`。若所有条件入边均跳过，或全部入边均跳过，节点也跳过。其余节点等所有入边有结果。所有合法选路必须各自到达一个终点。校验不设探索步数上限。

## 改图与交付

- 单点改目标用 `execute({replaceNode:{node,prompt,input,…}})` 提交完整节点。保留同名同类型节点的会话和原边。调整依赖、增加或删除节点时提交完整图。
- 宿主在采用时撤销已经过期的工作与交付。依赖过期交付的下游重新等待，独立任务沿用同一次执行。删除后重建的同名节点获得新实例。
- 指派中包含本轮实际采用的全部前序摘要与资产版本，共同祖先只出现一次。直接前驱还可带结构化结果。任务 Agent 通过 `finish({summary,assets,result?})` 暂存交付，未产生文件时传空数组。该次执行正常结束且依据仍然有效时，宿主才接纳交付。
- 主 Agent 用 `prompt({node,text})` 派追加工作。每项沿用提出时的目标和素材线索，排队逐项处理，交付回到主对话。相同正文的两次独立调用会产生两项工作。传输层使用同一收据重投时返回原结果，跨连接重投使用相同的 MCP `_meta["dev.xsb/call-id"]`。

## 内置工具的感知

工作流工具由 xSB 通过名为 `workflow` 的 MCP 服务提供，代理程序里显示为 `mcp__workflow__<工具>` 或 `workflow.<工具>`。系统提示词的"Your tools"一节和这个 MCP 服务 `initialize` 返回的 `instructions` 都说明：这些就是用户所说的工作流、编排、拆分任务、"workflow 技能"，它们不是磁盘上的 skill 文件，也不需要安装。工具描述以 "xSB workflow:" 开头。`ask` 不在其中：它是 xSB 自己的工具，来自 `xsb` 服务（见[向用户提问](ASK.md)）。

## 用户直接问任务 Agent

用户可以在任务会话里随时提问。任务 Agent 先给问题归类，再处理：

1. **和自己的任务有关**（目标、输入、素材、进度、交付）：自己处理。如果任务本身需要改变（交付内容、超出给定的输入或范围），调用 `escalate({message, pauseSelf: true})`，节点暂停，等主 Agent 决定，不悄悄改方向；当前交付需要作废时再加 `invalidateSelf`。
2. **和自己的任务无关，但和整体任务有关**（其他节点、计划、顺序、优先级、最终结果）：不自己处理，也不替主 Agent 回答。调用 `escalate({message})`，附上用户原话；节点照常工作。
3. **和两者都无关**：直接简短回答，不改动任何工作。

上报之后，任务 Agent 告诉用户主 Agent 会在主对话里处理。拿不准是第 1 类还是第 2 类时就上报，只有自己的任务必须改变时才暂停。

上报只有一个工具 `escalate`，两种情形的区别只在节点要不要停下来等。主会话收到通知 `{escalate, message, userSaid?, paused, invalidateSelf?}` 后，在主对话里回答用户，需要时用 `execute`（`replaceNode`）、`prompt`、`pause` 或 `resume` 调整工作流。`paused` 为真表示节点在等主 Agent：用 `execute({replaceNode})` 采用修改后的定义，或用 `resume({nodes:[该节点]})` 维持原任务。

## 任务 Agent 向用户提问

`ask` 不是工作流工具，是 xSB 自己的独立工具（见[向用户提问](ASK.md)），在工作流里也能用。任务 Agent 在执行指派时提问：这一轮没调 `finish` 就结束，也不算未完成，工作保持进行、等待回答；回答所在的那一轮接续同一项工作，在其中 `finish`。回答若赶在提问那一轮结束前送到，会并入那一轮，那一轮仍须 `finish`。节点被暂停或中枢重启后，等待取消，之后的回答按普通插话处理。

## 插话、暂停与恢复

主会话可以直接回答无关问题。工作流进行中，桌面主输入框发出的消息针对当前工作流：模型收到时前面附一句说明，处理这条插话期间暂缓图的派发和接纳。工作流结束后，主对话的消息就是普通消息，不再附说明。任务会话默认针对当前工作或交付，选“仅询问历史”可单独讨论旧版本。工作流的 `pause` 和 `resume` 可传 `nodes` 指定范围。任务需要改向时调用 `escalate({message, pauseSelf: true, invalidateSelf?})`，主 Agent 采用修改，或用 `resume({nodes:[…]})` 沿用原目标。多个暂停来源分别生效。

插话只有进入模型的对话才生效：没有送达的插话（被拒、失败、过期）不挡住图，恢复时也不续做。已送达的插话所在那一轮失败或被停止后，视图会标出 `interrupted`，界面提供"继续"。用户停止清掉的追加工作和未送达的通知，会随下一份工作流上下文告诉主 Agent。正在执行的指派被改图撤销后，节点的下一份指派会写明旧的已作废；节点会话换了上下文后，续做时重新发送整份指派。通知没有送达时会自动重投，最多 3 次。

宿主重启时为未完成工作增加全图暂停；已经完成且通知全部送达的图保持完成。查看工作流和历史可以在暂停期间进行。明确恢复后，已结束的待接纳交付重新校验，执行中断的工作在原会话续做。终点汇总与追加结果通过持久化通知送回主会话。

## 资产

使用 `asset_put(name,path)` 登记文件，以回执中的名称和版本交付。`asset_version_get(name)` 查询当前版本，任务对底图的首次选择会随该工作持久化。`asset_list(name)` 列出可访问版本，`asset_get(name,version)` 读取指定版本。主 Agent 或追加工作可选回旧版或清空当前指针。操作当前指针不会触发工作流重算。

在桌面制品列表或预览中引用文件，会把可移除的引用插入所选主对话或任务对话的草稿。发送已登记制品时，宿主收到卡片对应的名称与固定版本。同一条消息可以包含 `<asset>{"name":"主角定妆图","version":"v1"}</asset>` 和修改原话。主 Agent 可把精确引用传入任务 input。未选定版本时传递原话和定位线索，由使用素材的任务 Agent 查询或向用户确认。

## 输入与追加工作结果（2026-11-26）

输入接收与历史记录持久提交后投递，每会话一批在途 prompt 等待 ACP 插入回执。用户插话接收即保护 turn，回执到达即可续发，不等待整个 turn 结束。排队输入支持取消和仅队首的立即发送；立即发送由用户授权并保护当前 turn，在途队首占位直到确认或明确终结。

普通 Agent 调用不默认回传结果 prompt。追加工作完成后保存到节点 additionalResults，节点视图提供结果摘要，主会话不因此被唤醒或收到 additionalResult prompt。DAG 完成、分支选择与升级控制通知仍由图规则产生。

重启前未确认输入终结且不补发；不得恢复原邮件、加入欠交清单或将原文再次注入。明确 resume 可以继续保存的工作流 assignment；已接收用户插话的继续请求只引用原消息 ID，如果上下文已经缺失要求用户重新发送，不复制原文。

Hub 在发送 assignment 时直接生成 Markdown：任务要求、输入材料、前置成果与材料版本各自分段；追加任务和继续任务有明确标题，旧任务撤回提示仍可见。任务 ID、依据和模型等信息放在可展开的详情中。模型和 transcript 收到同一份正文，桌面端沿用普通 Markdown 渲染和原文复制，不按消息文案做正则解析。JSONL 图定义和工具参数继续使用结构化协议。
