# 会话与工作流

每次新建会话都会创建一个主 Agent。工作区可以保存多个主会话，它们各自拥有对话历史、模型后端和工作流，Agent 使用工作区中的文件。询问、写作或单次创作直接在当前会话完成。需要并行工作、条件选择或多步交付时，主 Agent 才建图。

主对话可在左栏右键菜单中重命名；名称会持久保存，后端生成的标题不再覆盖用户设置的名称，正在执行时也可改名。

首次用户输入先提供一个短的临时名称，Claude 和 Codex 适配器生成的名称通过 `session_info_update.title` 接管；标题在 turn 结束后到达也立即广播到界面。自动名称去掉多余空白并限制为 64 字符，空标题和系统提示词标题不采用。新建时指定名称或手动重命名都受保护；任务 Agent 保持图中的节点名称。

## 状态查询与控制 API

`Workflows` 是 Hub 的工作流服务对象，封装状态、调度与持久化；`workflow-state.ts` 负责图求值及状态转换，`acp-server.ts` 只映射协议。查询和更新通知使用同一份快照，UI 不从节点标签自行推断允许的动作。相关插话的 turn 开始、结束或失败时，服务也发布新快照，因为控制动作还取决于有效执行是否存在。

| 对象 API | ACP 方法 | 语义 |
| --- | --- | --- |
| `get(sessionId)` | `_dev.xsb/workflow/get` | 查询单个主会话的状态，无执行副作用 |
| `list()` | `_dev.xsb/workflow/list` | 查询已登记工作流 |
| `control(sessionId, "pause" / "resume", nodes?)` | `_dev.xsb/workflow/pause` / `resume` | 校验当前作用域、提交状态、调度并返回新快照 |

快照包含 `state`（`empty`、`proposed`、`running`、`paused`、`completed`）、整体 `controls: {pause,resume}` 和各节点的 `controls`。候选及历史版本仍独立展示。正在处理的主会话插话不能被误显示为等待恢复；任务节点仍有工作、追加、选择或未完成插话时，不算整体完成。

工作流到达有效终点时，插件将终点交付和主对话中的 Markdown 结果在同一事务中持久化。主 Agent 即使正在处理另一件事，用户也能看到结果。整体状态 `completed` 还要求各节点、追加工作、插话与待投递的控制通知均已结清。完成后暂停或恢复返回同一终态，重启也保留该状态。未完成工作需要显式恢复。

## 规划与执行

DAG 的任务节点和结束节点使用系统提示词声明的对话语言，名称简短且说明职责；中文对话用中文名称，英文对话用英文名称。`node`、边端点和工具参数引用同一名称；同一职责的节点改图时保留已有名称，以沿用会话。

主 Agent 调用 `plan({graphJsonl})` 保存一个候选，替换之前的候选。候选供预览，现有活动图继续运行。不带参数调用 `execute({})` 采用本轮看到的候选，也可以调用 `execute({graphJsonl})` 直接采用完整图。版本名由宿主按会话顺序分配（`plan-1`、`plan-2`…），同一图定义始终得到同一版本名；模型不起名，也不传版本名，宿主按本轮实际展示过的候选核对。每个主会话最多有一个候选和一个活动版本，候选的规划依据发生变化后须重新规划。

主会话的 `[xSB workflow]` 上下文不是每轮都附：

- **上下文里没有图时附完整 JSONL**：首轮、后端压缩上下文之后（`compaction_update`，或用量回落）、换后端会话续接之后，附上活动图和候选图的完整 JSONL（与提交格式相同）。工作流结束后也一样。
- **模型自己得不到的变化立即附**：暂停、出错、用户停止丢掉的追加工作和通知。
- **工作流进行中每 10 轮附一次**（`WORKFLOW_REFRESH_TURNS`），只带状态和变化了的定义。需要模型做选择或处理节点上报时，插件另发控制通知。
- **工作流结束后停止定期提醒**。终点结果以插件署名展示在主对话里，发布时主 Agent 不会收到 prompt，上下文交接也会跳过这条展示记录。

全文随时可凭 `graphRef` 用 `read_context` 读取。主对话的消息只交给主 Agent，任务 Agent 收不到；上下文里只有工作流的状态和交付摘要，没有任务 Agent 的对话。

主 Agent 从用户要拿到的结果倒推。JSONL 中每个节点或每条边独占一行。为每个节点（含终点）用 `inputSchema` 描述命名输入、类型和必填项，为每个任务节点用 `schema` 描述 `finish.result` 的类型、含义和单位。任务可以产出正文、布尔判断、金额、数组、对象或工作文件链接；按照下游或用户实际需要的类型交付。

建图时已经知道的值填入 `input`。前驱执行后才产生的值用数据边的 `bind` 声明，键是接收节点的输入字段名，值是从前驱 `result` 取值的 JSON Pointer。空字符串 `""` 取整个结果，`"/订单行"` 取该对象的“订单行”字段。需要换算、改写或判断时，由一个带输入和交付契约的任务执行。终点直接发布其命名输入，也可以提供 `schema` 对这个结果对象再做校验。

例如，用户要求从订单原文提取明细，再交给另一个节点核算金额。这张图先传订单行数组，再传整数金额。

```jsonl
{"node":"提取明细","prompt":"提取商品、数量和以分为单位的单价。","inputSchema":{"type":"object","properties":{"原始订单":{"type":"string"}},"required":["原始订单"],"additionalProperties":false},"input":{"原始订单":"铅笔 2 支，每支 3 元，橡皮 1 块，4 元。"},"schema":{"type":"object","properties":{"订单行":{"type":"array","items":{"type":"object","properties":{"品名":{"type":"string"},"数量":{"type":"integer","minimum":1},"单价（分）":{"type":"integer","minimum":0}},"required":["品名","数量","单价（分）"],"additionalProperties":false}}},"required":["订单行"],"additionalProperties":false}}
{"node":"核算总额","prompt":"按数量和单价核算订单总额，以分为单位交付。","inputSchema":{"type":"object","properties":{"明细":{"type":"array","items":{"type":"object","properties":{"品名":{"type":"string"},"数量":{"type":"integer","minimum":1},"单价（分）":{"type":"integer","minimum":0}},"required":["品名","数量","单价（分）"],"additionalProperties":false}}},"required":["明细"],"additionalProperties":false},"schema":{"type":"integer","minimum":0}}
{"node":"完成","kind":"end","inputSchema":{"type":"object","properties":{"总额（分）":{"type":"integer","minimum":0}},"required":["总额（分）"],"additionalProperties":false}}
{"from":"提取明细","to":"核算总额","bind":{"明细":"/订单行"}}
{"from":"核算总额","to":"完成","bind":{"总额（分）":""}}
```

“核算总额”收到两行明细后，调用 `finish({"summary":"两项合计 10.00 元","result":1000})`，终点得到 `{"总额（分）":1000}`。即使摘要只写“已完成”，下游取到的仍然是同一个整数。原样传值包括 `0`、`false` 和空字符串。确实没有外部输入的节点可以声明 `"inputSchema":{"type":"object","properties":{},"additionalProperties":false}`。

普通边等待有效交付。条件边还等待针对该次交付的选择。单选须选一个已有选项，多选源加 `"multi":true`，允许 `choose({from,cases:[]})`。若所有条件入边均跳过，或全部入边均跳过，节点也跳过。其余节点等所有入边有结果。每条可达路径上有效边和固定值须覆盖接收节点的必填字段，同一字段只有一个来源。所有合法选路必须各自到达一个终点。校验不设探索步数上限。

任务节点还可以指定 `model` 和固定的 `agent:{systemPrompt?,skills?:[{name,description,content}]}`。主 Agent 为新职责生成简短角色和可复用的技能正文，同名同类型节点继承省略的配置。配置、缓存与 ACP 能力边界见[任务 Agent 配置与缓存](WORKFLOW-AGENT-CONFIG.md)。

## 改图与交付

- 单点改目标用 `execute({replaceNode:{node,prompt,input,…}})` 提交完整节点。保留同名同类型节点的会话和原边。调整依赖、增加或删除节点时提交完整图。
- 宿主在采用时撤销已经过期的工作与交付。依赖过期交付的下游重新等待，独立任务沿用同一次执行。删除后重建的同名节点获得新实例。
- 任务 Agent 按本节点的命名输入工作。通过 `finish({summary,result})` 暂存交付，`summary` 面向用户，`result` 装入约定类型的实际内容。校验错误会返回给当前模型，它可以按报错位置修正再提交。该次执行正常结束且依据仍然有效时，宿主才接纳交付。
- 派发下游前，插件读取本次实际生效的边和接纳的交付，组装并按 `inputSchema` 校验完整输入。校验失败的节点保持未启动。成功时，指派保存输入及来源，ACP 把对应的任务目标、输入、前序摘要及输出要求送给模型。
- 主 Agent 用 `prompt({node,text})` 派独立的追加工作。追加指派保存提出时的目标与材料。契约图用当时已知的固定输入与已生效的前驱交付组装命名输入并校验。尚缺必填值时，调用返回字段错误，主 Agent 可以在材料到达后再派。追加结果记在节点的追加交付记录里，数据边只消费正式图任务的交付。相同正文的两次独立调用会产生两项工作。传输层使用同一收据重投时返回原结果，跨连接重投使用相同的 MCP `_meta["dev.xsb/call-id"]`。

契约图的终点把本次实际选路得到的命名输入发布到主对话，复杂结果可以包含对象、列表和工作文件链接。同一图中一旦使用 `inputSchema` 或 `bind`，其全部节点都需要声明输入契约，全部任务都需要声明交付契约。旧版图及其在途指派继续按原有定义运行，旧版终点仍列出所选路径上参与节点的交付。对话账本只接收通用的来源、条目标识与 Markdown。实时显示和重新打开主对话读取同一份正文。插件发布接口见[设计文档](DESIGN.md#插件向主对话发布-markdown)。

工作流工具的参数、收据、返回值，以及实际送达模型的工作流上下文和作用域说明，单独记录在项目的 `.xsb2/agents/<agentId>/workflow/<sessionId>.jsonl` 中。记录包含格式版本、来源、时间、会话和 turn ID。插件读取旧审计数据时也识别原对话日志里的 `dev.xsb/workflow-log`，无需改写既有对话。

## 内置工具的感知

工作流工具由 xSB 通过名为 `workflow` 的 MCP 服务提供，代理程序里显示为 `mcp__workflow__<工具>` 或 `workflow.<工具>`。系统提示词的"Your tools"一节和这个 MCP 服务 `initialize` 返回的 `instructions` 都说明：这些就是用户所说的工作流、编排、拆分任务、"workflow 技能"，它们不是磁盘上的 skill 文件，也不需要安装。工具描述以 "xSB workflow:" 开头。向用户征询决定时，Agent 使用后端原生提问工具，桌面端通过 ACP v2 显示问题。[向用户提问](ASK.md)

## 用户直接问任务 Agent

用户可以在任务会话里随时提问。任务 Agent 先给问题归类，再处理：

1. **和自己的任务有关**（目标、输入、素材、进度、交付）：自己处理。如果任务本身需要改变（交付内容、超出给定的输入或范围），调用 `escalate({message, pauseSelf: true})`，节点暂停，等主 Agent 决定，不悄悄改方向；当前交付需要作废时再加 `invalidateSelf`。
2. **和自己的任务无关，但和整体任务有关**（其他节点、计划、顺序、优先级、最终结果）：不自己处理，也不替主 Agent 回答。调用 `escalate({message})`，附上用户原话；节点照常工作。
3. **和两者都无关**：直接简短回答，不改动任何工作。

上报之后，任务 Agent 告诉用户主 Agent 会在主对话里处理。拿不准是第 1 类还是第 2 类时就上报，只有自己的任务必须改变时才暂停。

上报只有一个工具 `escalate`，两种情形的区别只在节点要不要停下来等。主会话收到通知 `{escalate, message, userSaid?, paused, invalidateSelf?}` 后，在主对话里回答用户，需要时用 `execute`（`replaceNode`）、`prompt`、`pause` 或 `resume` 调整工作流。`paused` 为真表示节点在等主 Agent：用 `execute({replaceNode})` 采用修改后的定义，或用 `resume({nodes:[该节点]})` 维持原任务。

## 任务 Agent 向用户提问

任务 Agent 需要用户决定才能完成本次指派时，使用 Claude 或 Codex 的原生同步提问。答复通过原 ACP 请求返回，当前 attempt 继续执行并在同一轮调用 `finish`。支持异步提问的 Codex 模型也可以先开展与答案无关的工作。任务节点的执行轮结束、暂停、停止或后端换绑时，仍待答的表单关闭，迟到的答复失效。[向用户提问](ASK.md)

## 插话、暂停与恢复

主会话可以直接回答无关问题。工作流进行中，桌面主输入框发出的消息针对当前工作流：模型收到时前面附一句说明，处理这条插话期间暂缓图的派发和接纳。工作流结束后，主对话的消息就是普通消息，不再附说明。任务会话默认针对当前工作或交付，选“仅询问历史”可单独讨论旧版本。工作流的 `pause` 和 `resume` 可传 `nodes` 指定范围。任务需要改向时调用 `escalate({message, pauseSelf: true, invalidateSelf?})`，主 Agent 采用修改，或用 `resume({nodes:[…]})` 沿用原目标。多个暂停来源分别生效。

插话只有进入模型的对话才生效：没有送达的插话（被拒、失败、过期）不挡住图，恢复时也不续做。已送达的插话所在那一轮失败或被停止后，视图会标出 `interrupted`，界面提供"继续"。用户停止清掉的追加工作和未送达的通知，会随下一份工作流上下文告诉主 Agent。正在执行的指派被改图撤销后，节点的下一份指派会写明旧的已作废；节点会话换了上下文后，续做时重新发送整份指派。通知没有送达时会自动重投，最多 3 次。

宿主重启时为未完成工作增加全图暂停，期间仍可查看图和历史。明确恢复后，已结束的待接纳交付重新校验，执行中断的工作在原会话续做。升级时，旧版仍待投递且可核实的终点通知按原交付 ID 发布一次。已确认插入模型的旧通知沿用原有历史。

## 文件

桌面「文件」面板列出当前主会话和它的工作流节点通过后端工具生成或修改的本地文件。Hub 从 ACP v2 的 `tool_call_update` 读取结构化 `diff.changes`，按 `toolCallId` 合并分段更新，在工具成功后采用变更。同一路径只显示一项，移动会更新路径，删除会将路径移出列表。

Claude 的 `NotebookEdit` 和向空文件写入内容的 `Edit` 有时只提供工具名和结构化输入路径，此时按成功调用的目标收录。Codex 生图结果带有已保存的本地路径时也会显示。工具只上报命令、读取位置或内联图片时，无法据此确认生成了哪个文件。

文件直接从原位置打开。任务指派、交付摘要与普通对话可以引用工作区路径或文件链接；文件面板可从原始会话事件重新生成。旧版登记过的文件保留在磁盘原处。

## 输入与追加工作结果（2026-11-26）

输入接收与历史记录持久提交后投递，每会话一批在途 prompt 等待 ACP 插入回执。用户插话接收即保护 turn，回执到达即可续发，不等待整个 turn 结束。排队输入支持取消和仅队首的立即发送；立即发送由用户授权并保护当前 turn，在途队首占位直到确认或明确终结。

普通 Agent 调用不默认回传结果 prompt。追加工作完成后保存到节点 `additionalResults`，节点视图提供结果摘要。DAG 终点通过插件发布主对话正文。只有需要主 Agent 行动的分支选择和升级才走控制通知投递。

重启前未确认输入终结且不补发；不得恢复原邮件、加入欠交清单或将原文再次注入。明确 resume 可以继续保存的工作流 assignment；已接收用户插话的继续请求只引用原消息 ID，如果上下文已经缺失要求用户重新发送，不复制原文。

Hub 从已保存的指派生成 ACP 消息，按任务要求、命名输入、前置成果与输出要求分段。追加任务和继续任务有明确标题，旧任务撤回提示仍可见。模型和 transcript 收到同一份正文。数据绑定与派发直接读取插件中的结构化值，不需要解析摘要或界面 Markdown。
