# 预设团队：组织、继承与写法

> 历史设计记录。当前版本的编排接口、会话和交付约定见[工作流指南](WORKFLOWS.md)。

预设团队是一套现成的角色。有两个来源，组织完全一样：

| 来源 | 位置 | 谁写 |
|-|-|-|
| 应用自带 | 代码旁边的 `presets/`（开发时是 `packages/hub/presets/`，打包后是 `dist/presets/`） | 随 xSB 发布 |
| 你自己的 | `~/.xsb/presets/`（设了 `XSB_HOME` 就跟着它） | 你 |

把应用自带的 `presets/film/` 整个复制到 `~/.xsb/presets/film-mine/`，就多出一支团队。团队标识来自文件夹名，中英文版本一起分发。源模板改完后下次查看就能读到新版本；已有项目副本需要显式同步。

## 目录

```
<来源>/<团队>/<语言>/team.json
<来源>/<团队>/<语言>/roles/<角色>/role.json
<来源>/<团队>/<语言>/roles/<角色>/instructions.md
<来源>/<团队>/<语言>/roles/<角色>/skills/<技能>/SKILL.md   （技能用到的文件放在它旁边）
<来源>/<团队>/<语言>/roles/<角色>/avatar.png              （可选：role.json 里 "avatar": "role" 时用）
<来源>/<团队>/<语言>/evals/<场景>.json                     （可选：场景评估）
```

单语言团队也可以直接把 `team.json`、`roles/`、`evals/` 放在 `<来源>/<团队>/` 下，在 `team.json` 写 `"language": "zh-CN"`（省略时为 `en`）。内置与用户团队使用同一个加载器和数据结构。

团队标识由小写字母、数字、`-`、`_` 组成，以字母或数字开头。`en` 和 `zh-CN` 保留给旧版语言目录，不作为新团队标识。

旧的 `<来源>/<语言>/<团队>/` 仍可读取，无需搬动已有用户模板。同一个团队同时存在新旧目录时，同语言的新目录优先，并报告重复警告；优先使用项目语言，再使用团队根目录的单语言版本，最后回退到其他语言。选中的文件损坏时报告错误，不会悄悄使用其他副本。

`team.json`：

```json
{
  "title": "电影创作",
  "description": "……",
  "extends": "film",
  "roles": [{ "role": "director", "name": "导演", "requires": [{ "command": "ffmpeg", "install": "……" }] }],
  "assets": { "brief": "创作简报" }
}
```

- **语言**：`<语言>` 是 `en` 或 `zh-CN`。项目用哪种语言，就读哪种语言的团队。
  - 你自己的团队可以只写一种语言，另一种语言的项目照样能用，界面上会注明它是哪种语言。
  - 应用自带的团队，中英两份结构必须一致，由测试守着。
- **`requires`**：这个角色要用到的本机程序。xSB 只在 `PATH` 里查找，不会替你安装。
- **`assets`**：给团队的资产类型起名字。技能里 `produces` 和 `inputs` 用到的每种类型都应该有名字。

## 项目副本与同步

首次运行 `xsb team use <团队>`（桌面端“使用角色”或“建立团队”）时，模板会复制到 `<项目>/.xsb2/templates/<团队>/`。角色、技能和技能旁的资源文件一并复制，继承团队的角色也会合成完整副本。项目自己的修改仍放在 `.xsb2/roles/<角色>/`，优先于项目模板副本。

应用升级或修改用户模板不会自动改变项目副本，反复“建立团队”也不会覆盖。旧项目在首次启动新版 Hub 时建立副本，已有的项目覆盖版本保留。模板来源被移除后，项目仍可使用副本。

更新副本有两种入口：

```sh
xsb team sync film --preview  # 只查看将覆盖、丢弃、移除的角色
xsb team sync film            # 交互确认，默认取消
xsb team sync film --yes      # 明确接受覆盖风险，适用于脚本
```

桌面端在已使用的专家团旁显示“同步模板”，先列出角色范围，并提示“自定义改动会丢失”，再由用户选择“覆盖并丢弃自定义改动”。说明、技能及其文件、工具配置、头像都会被覆盖；需要保留的内容请先备份。运行中的智能体不会自动重启，角色页“应用修改”或重启后使用新配置。

匹配不增加模板 ID：使用来源根目录类别（内置 / 用户）、专家团文件夹名、角色文件夹名。开发与打包的内置绝对路径可以不同，来源类别保持不变。同名角色继续由父目录区分；项目同时使用无继承关系的同名角色团队时拒绝，并在同步引入新冲突时同样拒绝。目录改名会成为另一个模板，不会误匹配到旧副本。

从模板编辑生成的 `.xsb2/roles/<角色>/` 会带 `.template-origin.json`，记录上述目录来源；同步只丢弃来源相同、角色代码相同的覆盖版本。项目独立创建的同名角色保持自己的来源。确认前后模板或项目文件变化时，需要重新预览和确认；写入失败会恢复旧副本。

## 在别的团队上改：`extends`

团队可以基于另一支团队，只放不同的部分。同名角色按三条规则叠加：

1. `role.json`：你的字段覆盖基础团队的；`mcpServers` 按工具服务的名字合并。
2. `instructions.md`：你的内容接在基础团队的说明后面。你的说明只补充事实，不要推翻原有流程。
3. `skills/`：两边的技能合在一起，同名的由你的替换。

只出现在一边的角色，原样使用。你自己的团队可以基于应用自带的；应用自带的团队只能基于应用自带的。

**注意**：你的团队不能和应用自带的团队同名。同名的话，你就会在不知情的情况下拿不到新版本对它的改进。要改应用自带的团队，就派生一支：

```
xsb team new film-mine --extends film
```

桌面端预设页的"派生"按钮也是这样做的。

## 冲突与问题

- **两支团队都有同名角色**：如果它们之间没有继承关系，一个项目不能同时使用这两支（报错 `team_clash`）。
- **出错的地方**：只跳过出错的那支团队或那个角色，其余照常可用，问题会列出来：
  - 命令行：`xsb team check [<团队>]`，有错误时退出码为 1；
  - 桌面端：预设页。

不运行就能查出的问题有这些：
- `team.json` 列出了不存在的角色；
- 角色读取失败；
- 技能没有写 `description`；
- 资产类型没有起名字；
- 某种输入没有任何角色产出（这时要由用户提供）；
- 说明或技能过长（超过约 8000 字时，单条规则容易被忽略）；
- `"avatar": "role"`，但角色目录里没有 `avatar.png`。

## 新增自己的专家团

例如在 `~/.xsb/presets/research/` 中创建：

```text
research/
  team.json
  roles/
    researcher/
      role.json
      instructions.md
      skills/
        investigate/SKILL.md
```

`team.json` 写入 `{"title":"研究专家团","language":"zh-CN","roles":[{"role":"researcher","name":"研究员"}]}`；`role.json` 可以从 `{}` 开始，在 `instructions.md` 写角色的工作方式。运行 `xsb team check research` 检查，再用 `xsb team use research` 引入项目。新增、修改、移除源文件会在下次查看时读到；已有项目通过“同步模板”更新副本。

将来插件中心可以把专家团安装到这个用户目录，再交给现有加载、校验和继承机制使用。当前支持本地文件扩展，尚未实现在线安装、版本管理或更新。

## 提示词怎么写

各层负责的事不同，规则写在模型做决定时会读到的地方：

| 层 | 写什么 | 不写什么 |
|-|-|-|
| xSB 的系统提示（中枢生成） | 所有团队通用的协作方式、工具来源、工作规则 | 不用你写 |
| `instructions.md`（角色说明） | 这个角色是谁、流程、关口、贯穿始终的原则 | 只和某类任务有关的做法 |
| `SKILL.md`（技能） | 某类工作的做法；带 `produces` 的技能会随产出该类型的任务一起送达 | 模型和工具的数值限制 |
| 工具说明（工具服务提供） | 工具是谁的、什么时候用、数值限制 | 团队的流程 |

五条规则：

1. **能用机制保证的，不靠提示词。** 任务状态、并发由 xSB 保证；提示词只管需要判断的事。
2. **规则写在模型做这个决定时会读到的地方**，见上表。
3. **每条规则附一句原因。** 例如"已经开始的生成撤不回，所以……"。知道原因，模型才能把规则用到没写到的情形。
4. **说要做什么，少说不要做什么。** 例如写"报告时写明用什么方法检查过"，而不是"不要说看过"。
5. **需要固定格式的输出，给一个模板。** 授权清单和升清询问的写法见电影团队导演说明里的例子。

## 场景评估：`evals/`

写完一支团队，用场景评估来量它的效果，不要只凭感觉。每个文件一个场景：

```json
{
  "id": "S9",
  "title": "要别人交付东西时用任务，不用消息",
  "role": "director",
  "messages": ["让摄影师重出 1-1 和 1-2 的首帧，出好告诉我。"],
  "peers": ["cinematographer"],
  "spent": 0,
  "expect": [{ "calls": "dispatch_task" }, { "noCalls": "send_message" }]
}
```

检查规则有这几种，正则不区分大小写：
- `firstTool`：在名字符合 `among` 的工具中，第一个调用的要符合 `is`；
- `calls`：调用过符合的工具；
- `noCalls`：没有调用过符合的工具；
- `atMost`：某个工具最多调用几次；
- `says`：回复里说了符合的内容；
- `saysNot`：回复里没有说符合的内容。

工具名会去掉智能体程序加的前缀再比较：`mcp__xsb__dispatch_task` 和 `mcp.xsb.dispatch_task` 都按 `dispatch_task` 算。

```
xsb team eval film-mine --backend claude --runs 5
```

- **基础团队的场景**：基于别的团队时，也会跑基础团队的场景；你的团队里同一 `id` 的场景会取代它。
- **怎么运行**：每次运行都在一个临时项目里进行。浏览器、出图、出视频都换成替身，不产生生成费用；`peers` 里的角色在场，但不会真的运行。
- **会花钱**：用的是真实后端的模型，会产生模型费用。
- **怎么读结果**：同一个场景至少跑 5 次，看通过率。只跑一次的结果，分不清是改动起了作用，还是模型本身的波动。改了一条规则，就前后各跑一遍对比；一条规则去掉之后通过率不变，说明它没起作用，可以删掉。
