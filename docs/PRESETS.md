# 预设团队：组织、继承与写法

预设团队是一套现成的角色。有两个来源，组织完全一样：

| 来源 | 位置 | 谁写 |
|-|-|-|
| 应用自带 | 代码旁边的 `presets/`（开发时是 `packages/hub/presets/`，打包后是 `dist/presets/`） | 随 xSB 发布 |
| 你自己的 | `~/.xsb/presets/`（设了 `XSB_HOME` 就跟着它） | 你 |

把应用自带的 `presets/zh-CN/film/` 原样复制到 `~/.xsb/presets/zh-CN/`，改一个团队标识，就多出一支团队。改完文件不用重启，下一次用到就生效。

## 目录

```
<来源>/<语言>/<团队>/team.json
<来源>/<语言>/<团队>/roles/<角色>/role.json
<来源>/<语言>/<团队>/roles/<角色>/instructions.md
<来源>/<语言>/<团队>/roles/<角色>/skills/<技能>/SKILL.md   （技能用到的文件放在它旁边）
<来源>/<语言>/<团队>/roles/<角色>/avatar.png              （可选：role.json 里 "avatar": "role" 时用）
<来源>/<语言>/<团队>/evals/<场景>.json                     （可选：场景评估）
```

`team.json`：

```json
{
  "title": "电影创作",
  "description": "……",
  "extends": "film",
  "roles": [{ "role": "director", "name": "导演", "requires": [{ "command": "ffmpeg", "install": "……" }] }],
  "assets": { "brief": "创作简报" }
}
```

- **语言**：`<语言>` 是 `en` 或 `zh-CN`。项目用哪种语言，就读哪种语言的团队。
  - 你自己的团队可以只写一种语言，另一种语言的项目照样能用，界面上会注明它是哪种语言。
  - 应用自带的团队，中英两份结构必须一致，由测试守着。
- **`requires`**：这个角色要用到的本机程序。xSB 只在 `PATH` 里查找，不会替你安装。
- **`assets`**：给团队的资产类型起名字。技能里 `produces` 和 `inputs` 用到的每种类型都应该有名字。

## 在别的团队上改：`extends`

团队可以基于另一支团队，只放不同的部分。同名角色按三条规则叠加：

1. `role.json`：你的字段覆盖基础团队的；`mcpServers` 按工具服务的名字合并。
2. `instructions.md`：你的内容接在基础团队的说明后面。你的说明只补充事实，不要推翻原有流程。
3. `skills/`：两边的技能合在一起，同名的由你的替换。

只出现在一边的角色，原样使用。你自己的团队可以基于应用自带的；应用自带的团队只能基于应用自带的。

**注意**：你的团队不能和应用自带的团队同名。同名的话，你就会在不知情的情况下拿不到新版本对它的改进。要改应用自带的团队，就派生一支：

```
xsb team new film-mine --extends film
```

桌面端预设页的"派生"按钮也是这样做的。

## 冲突与问题

- **两支团队都有同名角色**：如果它们之间没有继承关系，一个项目不能同时使用这两支（报错 `team_clash`）。
- **出错的地方**：只跳过出错的那支团队或那个角色，其余照常可用，问题会列出来：
  - 命令行：`xsb team check [<团队>]`，有错误时退出码为 1；
  - 桌面端：预设页。

不运行就能查出的问题有这些：
- `team.json` 列出了不存在的角色；
- 角色读取失败；
- 技能没有写 `description`；
- 资产类型没有起名字；
- 某种输入没有任何角色产出（这时要由用户提供）；
- 说明或技能过长（超过约 8000 字时，单条规则容易被忽略）；
- `"avatar": "role"`，但角色目录里没有 `avatar.png`。

## 提示词怎么写

各层负责的事不同，规则写在模型做决定时会读到的地方：

| 层 | 写什么 | 不写什么 |
|-|-|-|
| xSB 的系统提示（中枢生成） | 所有团队通用的协作方式、工具来源、工作规则 | 不用你写 |
| `instructions.md`（角色说明） | 这个角色是谁、流程、关口、贯穿始终的原则 | 只和某类任务有关的做法 |
| `SKILL.md`（技能） | 某类工作的做法；带 `produces` 的技能会随产出该类型的任务一起送达 | 模型和工具的数值限制 |
| 工具说明（工具服务提供） | 工具是谁的、什么时候用、数值限制 | 团队的流程 |

五条规则：

1. **能用机制保证的，不靠提示词。** 任务状态、并发由 xSB 保证；提示词只管需要判断的事。
2. **规则写在模型做这个决定时会读到的地方**，见上表。
3. **每条规则附一句原因。** 例如"已经开始的生成撤不回，所以……"。知道原因，模型才能把规则用到没写到的情形。
4. **说要做什么，少说不要做什么。** 例如写"报告时写明用什么方法检查过"，而不是"不要说看过"。
5. **需要固定格式的输出，给一个模板。** 授权清单和升清询问的写法见电影团队导演说明里的例子。

## 场景评估：`evals/`

写完一支团队，用场景评估来量它的效果，不要只凭感觉。每个文件一个场景：

```json
{
  "id": "S9",
  "title": "要别人交付东西时用任务，不用消息",
  "role": "director",
  "messages": ["让摄影师重出 1-1 和 1-2 的首帧，出好告诉我。"],
  "peers": ["cinematographer"],
  "spent": 0,
  "expect": [{ "calls": "dispatch_task" }, { "noCalls": "send_message" }]
}
```

检查规则有这几种，正则不区分大小写：
- `firstTool`：在名字符合 `among` 的工具中，第一个调用的要符合 `is`；
- `calls`：调用过符合的工具；
- `noCalls`：没有调用过符合的工具；
- `atMost`：某个工具最多调用几次；
- `says`：回复里说了符合的内容；
- `saysNot`：回复里没有说符合的内容。

工具名会去掉智能体程序加的前缀再比较：`mcp__xsb__dispatch_task` 和 `mcp.xsb.dispatch_task` 都按 `dispatch_task` 算。

```
xsb team eval film-mine --backend claude --runs 5
```

- **基础团队的场景**：基于别的团队时，也会跑基础团队的场景；你的团队里同一 `id` 的场景会取代它。
- **怎么运行**：每次运行都在一个临时项目里进行。浏览器、出图、出视频都换成替身，不产生生成费用；`peers` 里的角色在场，但不会真的运行。
- **会花钱**：用的是真实后端的模型，会产生模型费用。
- **怎么读结果**：同一个场景至少跑 5 次，看通过率。只跑一次的结果，分不清是改动起了作用，还是模型本身的波动。改了一条规则，就前后各跑一遍对比；一条规则去掉之后通过率不变，说明它没起作用，可以删掉。
