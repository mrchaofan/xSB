# Markdown 工作流的节点、交付和选路

主 Agent 用 JSONL 建图，任务 Agent 读取 Markdown 要求和实际参数，交付 Markdown 正文。以下接口适用于含 `requirements` 的新图。已有工作流的操作和兼容格式见[工作流指南](WORKFLOWS.md)。

## 1. 节点相当于一次函数调用

| 字段 | 谁写、何时写 | 内容 |
| --- | --- | --- |
| `node` | 主 Agent 建图时 | 唯一的节点名，供连边、选路和界面显示 |
| `requirements` | 主 Agent 建图时 | 一段 Markdown。声明需要几项参数、各自含义、如何提供，还要说明本节点完成什么工作、交付什么产物 |
| `input` | 主 Agent 只在入口任务的图定义里填写。其他节点由 Hub 在派发时组装 | 本次调用的 Markdown 实参，例如剧本链接、画风或出行日期 |
| `output` | 来源任务 Agent 调用 `finish({output})` | 本节点本次执行的 Markdown 交付，保存在自身的运行状态中，可以包含文件链接 |
| `choice` | 有条件出边时，来源任务 Agent 调用 `choose({node})` | 本节点为这次交付选择的目标节点名，保存在与 `output` 相同的节点执行记录上 |

主 Agent 在 JSONL 中写任务节点时，`node` 和 `requirements` 必填。整张图连边后，只有入度为零的任务节点可以声明字符串 `input`，没有外部参数的入口可省略它。非入口节点即使写的是空字符串，建图校验也会指出节点名和违规字段。条件边运行时被跳过不会改变节点在图定义里的入度。`output` 和 `choice` 是运行状态字段。节点已有的模型、角色和技能配置仍属于执行配置。

例如，「生成角色图」本身是入口任务时，它可以接收两项实参。第一项接受剧本文字或文件，第二项接受画风描述。换剧本时只需换实参。

```json
{
  "node": "生成角色图",
  "requirements": "需要两项输入。① 剧本，传正文或文件链接。② 画风，传文字描述。为每位主要角色生成一张设定图，按角色名交付图片链接。",
  "input": "1. 剧本：[春潮剧本](./春潮.md)\n2. 画风：黑白水墨，全身像。"
}
```

任务会话里显示「开始 生成角色图」。同一次 ACP 请求将任务要求和本次实际输入作为仅供模型读取的补充文本。实际图片由文件承载，`output` 可写成「林秋 — [角色设定图](./角色图/林秋.png)」。

## 2. 后继就绪时读取直接前驱

每个任务只把交付写到自身节点的 `output`。调度器据此更新边的就绪状态。后继还在等待时，自身没有本次调用的实参，也没有供前驱逐项写入的输入缓冲区。

| 派发时的情况 | 本次指派的 `input` |
| --- | --- |
| 入口任务 | 图定义里的 `input` 原文，省略时为空 |
| 有一个生效的直接前驱 | 读取该前驱本次已接纳的 `output` 原文 |
| 有多个生效的直接前驱 | 读取各前驱本次已接纳的 `output`，按图保存的拓扑顺序以来源节点名分段拼成一份 Markdown。完成先后不影响顺序。同一来源交付只取一次，两个节点恰好产出相同正文时分别保留 |

例如，若「生成角色图」同时依赖「编写剧本」与「确定画风」，图定义里只有它的节点名和要求。即使剧本先完成，正文也只存在「编写剧本」上。等画风也完成，Hub 才读取剧本链接与画风说明，一次生成绘图指派。Hub 将本次实参和来源交付 ID 冻结在指派记录中，供执行和恢复使用。图定义与运行指派可以在界面分别查看。

节点只等待与自身有关的依赖，互不依赖的入口和分支可各自推进。跳过的边不贡献正文。需要更早的材料时，在图上连接其生产节点，或在直接前驱的交付要求中说明应保留哪些事实和文件链接。长正文沿用全文引用和分页读取机制。

## 3. 普通边和终点

任务 Agent 完成工作后调用 `finish({output})`，其中 `output` 是非空 Markdown。Hub 先在本节点本次执行上持久暂存，正常结束且指派和依赖仍有效时接纳。普通出边在交付获接纳后自动放行。同一来源兼有普通出边和条件出边时，普通出边只依赖已接纳的 `output`，条件出边还依赖有效的 `choice`。

汇合沿用现有 DAG 规则。某节点有条件入边且这些条件入边全部跳过，或者它的所有入边均跳过，该节点也跳过。其他节点等全部入边状态确定后，用生效的输入开始工作。图有多条合法选路时，每种选择都应到达一个有效终点。

终点写作 `{"node":"交付行程","kind":"end"}`，由 Hub 直接发布到主对话。一个生效的直接前驱就发布它的 `output`；多个生效的直接前驱就按来源分段发布。要把若干材料编辑成一份统一成品，在终点前放一个有明确交付要求的任务节点。完成记录按终点交付 ID 去重。

## 4. 条件边由来源任务 Agent 选择

条件边写作 `{"from":"整理出行需求","to":"规划跨城路线","case":"出行期间要游览两座或更多城市"}`。Hub 从当前任务节点的条件出边取「目标节点名 + 文字 case」，展示给执行该节点的任务 Agent。同一来源通往同一目标的多种适用情形可以写在一段 `case` 里。若分开写在多条边上，Hub 将其按目标名合并为一个候选，用换行列出各段条件。

1. 来源任务 Agent 提交 `finish({output})`。有条件出边时，工具回执列出候选，提示它对照自己刚提交的正文，在本轮调用 `choose(下一个节点名)`。MCP 工具只有一个业务参数，例如 `choose({"node":"规划跨城路线"})`。
2. Hub 从当前获授权的任务指派确定起点，用传入的节点名确定终点。在同一事务中校验该节点实例、本次执行、已提交的交付和候选仍然有效，把目标名写入**起点**的 `choice`。即使两个来源同时选择同名目标，各自也只更新自己的记录。主会话无需接收选路通知或保存发起方映射。追加工作和历史对话没有正式图指派的选路权限。
3. 交付获接纳且有匹配的 `choice` 时，通往所选目标的条件边放行，其他同组条件边标为跳过。如果本轮已经正常结束、交付已接纳但还没有选择，节点显示「待选路」。Hub 在可运行时给**同一个来源任务 Agent** 一次只做选路的指派，带上持久保存的正文和当前候选。这时成功提交 `choose` 即可放行条件边。仍无法判断时可以补问或暂停该节点。新信息若改变交付内容，须回退该节点再形成新交付。

每次交付最多选一个目标。重复提交同一次选择是幂等的，越界目标或同次交付上相互冲突的选择返回错误。改变已生效的选择须回退。执行标识、交付标识、工具收据都由 Hub 保存，工具参数只写目标节点名。

## 5. 完整示例

两个入口任务可并行执行。「整理出行需求」掌握目的地和日期，负责选择市内或跨城。「整理出行偏好」单独整理用户偏好。被选中的规划节点需要两份交付。

```jsonl
{"node":"整理出行需求","requirements":"需要旅游地点和出行时间。交付确定的城市、日期以及用户指定的游览顺序。缺项时先补问。","input":"- 旅游地点：杭州、苏州，先杭州后苏州。\n- 出行时间：5 月 2 日至 4 日。"}
{"node":"整理出行偏好","requirements":"需要用户提供的偏好。交付安排路线时应遵守的交通和行程强度要求。","input":"优先公共交通，每天最多两个景点。"}
{"node":"规划市内路线","requirements":"需要城市、日期和出行偏好。按天交付符合偏好的市内路线。"}
{"node":"规划跨城路线","requirements":"需要城市、日期、游览顺序和出行偏好。按天交付路线，标明跨城交通。"}
{"node":"交付行程","kind":"end"}
{"from":"整理出行需求","to":"规划市内路线","case":"整个行程只游览一座城市"}
{"from":"整理出行需求","to":"规划跨城路线","case":"出行期间要游览两座或更多城市"}
{"from":"整理出行偏好","to":"规划市内路线"}
{"from":"整理出行偏好","to":"规划跨城路线"}
{"from":"规划市内路线","to":"交付行程"}
{"from":"规划跨城路线","to":"交付行程"}
```

1. 「整理出行需求」的任务 Agent 调用 `finish({"output":"5 月 2 日至 4 日，共三天。先游杭州，再游苏州。"})`。它读到上述两个候选及其条件，调用 `choose({"node":"规划跨城路线"})`。需求节点自己的记录保存这段正文和目标名。
2. 即使需求节点已完成，只要偏好还在执行，跨城节点就继续等待。偏好节点调用 `finish({"output":"优先公共交通，每天最多两个景点。"})` 并获接纳后，Hub 才为「规划跨城路线」生成本次 `input`。

   > **整理出行偏好**
   >
   > 优先公共交通，每天最多两个景点。
   >
   > **整理出行需求**
   >
   > 5 月 2 日至 4 日，共三天。先游杭州，再游苏州。

3. 市内路线的条件入边已跳过。即使它也有来自偏好节点的普通入边，仍然跳过。「规划跨城路线」对照两份材料完成路线，把按天安排写入自己的 `output`。「交付行程」就绪后读取并发布这份正文。
4. 假如用户把目的地改成只游杭州，更新入口实参，回退「整理出行需求」。旧的需求交付、选路、跨城路线和当前终点交付一并失效。偏好节点的交付保持有效。需求节点重新交付并选择「规划市内路线」后，市内节点取得新需求和原偏好，其交付成为新的终点结果。

## 6. 暂停、恢复和回退

**暂停保存进度。** Hub 持久化节点本次执行的来源依据、已提交的 `output`、`choice` 和接纳阶段。暂停提交后冻结工具权限及受影响的派发。重启后从同一记录恢复，沿用显式恢复和 ACP 输入回执规则。

| 暂停点 | 同一次有效执行恢复后的动作 |
| --- | --- |
| 尚未提交 `finish` | 续做原任务，按执行记录核对已产生的文件或其他效果 |
| `finish` 已持久保存，尚欠 `choose` | 给原节点任务 Agent 保存的正文和当前候选，只补选路 |
| `output` 与所需的 `choice` 已保存 | 已接纳时直接重算就绪边。尚属暂存时，使用已记录的正常结束回执结算；若在正常结束前被暂停，在恢复后的授权轮中核对保存的提交，正常结束后再接纳 |
| 暂停发生在汇合节点等待期间 | 恢复后重新检查直接入边，全部确定且满足运行条件才组装这次输入 |

同一次有效执行可以在恢复时换一个获授权的 turn。续做时校验节点实例、执行代次、依赖、当前后端和工具权限。恢复动作本身不能把失败的提交自动升级为有效交付。需要明确恢复的失败或执行效果未知时，按既有生命周期契约处理。

**回退撤销当前结果。** 回退到节点 X 时，Hub 在同一次状态更新中重置这部分图。

1. 撤销 X 及受影响后继的在途正式指派、选路任务和待发布结果。重新派发使用新的指派和执行标识。旧工具调用或迟到的结束回执失去对当前工作的写入资格。
2. 清除这些节点当前的 `output`、`choice`、暂存结果和已派发的输入快照，重新求值各条边。汇合节点按本次实际采用的前驱交付及其顺序判断是否重算。例如 A 选 B、跳过 C，B 和 C 汇入 D 时，单独回退 C 会保留 D 的有效产物。回退 A 重新选路则会重新核对 D 的输入。
3. 保留入口定义的实参及回退范围以外的独立节点交付。全图回退则清除全图的运行结果。重新执行得到相同正文时，也属于新的交付，必须重新选择条件边。
4. 回退触及已完成终点时，当前完成状态一并撤销。上一轮已发布的用户可见记录留作历史并标明已失效。当前节点视图、恢复指派、下游组装和新的终点发布都只读取当前代次。

主 Agent 可以调用 `rollback({nodes:["整理出行需求"]})` 局部回退，或调用 `rollback({})` 回退全图。命令行通过 `xsb workflow rollback SESSION_ID 整理出行需求` 执行同一操作；省略节点名时回退全图。改图采用时一起核对节点要求、入口实参、依赖和条件候选。候选集合或 `case` 变化而使原裁决依据失效时，对来源节点执行同样的回退和清理。

## 7. 查看结果和继续旧工作流

用 `plan` 保存候选，`execute` 采用候选或修改节点。Hub 检查全图的入口输入、节点名唯一、端点存在、无环，以及每条合法选路均到达一个有交付来源的终点。独立追加用 `prompt({node,text})`，节点通过 `finish({output})` 交付到本次追加记录。

桌面候选图的入口显示已给定的实参。运行图显示任务要求、实际派发的输入及其来源、本节点的输出和已选出边。回退前的结果可以在版本选择器的历史快照中查看。

已有摘要图和带 `inputSchema`、`schema`、`bind` 的旧契约图沿用创建时的工具、主会话选路、多选与终点语义。同名同类型任务在同一协议内可以复用会话。采用另一种工作流协议时，Hub 为新图创建新的任务会话；原任务会话保存在历史版本里。
