## 二、应当修（一致性/标注）

- 退出时"不继续"，用户排队消息无痕消失（`kernel.ts:834 abandon` 不写 Discarded）。
- 已插入未处理的输入续接后账本变"未读丢弃"，界面照常显示（`ledger.ts:39-50`）。
- 定向追加过期以"停止"为续接理由，分割线和交接都说"已停止"（`session.ts:1019-1027`）。
- 界面看不出哪些输入模型还没看到：待发/插话回执前与已送达同样式；"已丢弃"文案一律写"停止时"。
- 正常结束后接续的插话仍标"插话"（`resume` 不清 `steered`）。
- 收件箱积压拆成多条输入，英文提示 "[xsb] While you were not working here…" 进了用户可见正文。
- 分割线文案无"已被压缩"字样；`renewed`"太长"也用于并非太长的场景。
- 中枢写转录不 fsync，边界/丢弃记录与已 fsync 的状态在断电时可能顺序不一致。
- 进程内事务失败后继续运行，重启补写旧记录覆盖新状态（`store.ts:164,191`）。
- 快速退出再开：新中枢抢锁等待 3 秒 < 后端宽限 3 秒 + 关停，可能报"中枢未启动"（`daemon.ts:28`）。
- 发送失败时界面恢复草稿，但中枢可能已落盘并执行；再按发送会用新 id 再投一次。
- 工作区插件确认可绕过：指纹只含 plugin.json，不含它启动的文件；确认界面不显示 env/headers。

## 三、结构（设计标准："每个类不可或缺、实现简单"）

1. **两套编排并存**：Kernel 的智能体任务（`dispatch/createJob/replace/subscribe/complete`）在 src 中零调用（已核实），连带 gates、`jobs.ts`、`awaitResult`、`sync` 投递都不可达；工作流另有一套状态机。但 AGENTS.md、TURN-LIFECYCLE、TASK-GRAPH 与注入模型的 `TASK_LIFECYCLE_RULES` 仍以它为准，`jobsAtOnce` 还在设置里可调。需要定 Kernel 的定位：收缩为"用户任务 + 邮箱 + 台账 + 停止"，或把工作流节点建模为 Kernel task。
2. **提示词引用不存在的工具**（已核实）：`prompts.ts` 的 `get_asset`、`task_status`、`recall`；实际是 `asset_get` 等。
3. **Hub 服务定位器 + Session/Workflows 双向耦合**：`session.ts`（1256 行）十处 `this.hub.workflows?.`，`workflows.ts` 反向操作 session 内部；工作流字段进了 Kernel 的 `MailItem`。
4. **契约手抄多份**：IPC 方法表（preload / main switch / bridge 类型 / mock）、协议字符串、节点类型、一等后端描述，扩展需散改 7–9 处。
5. 死代码与过时注释：记忆（memoryHint）、两套资产模型、`assetNames`、旧任务栏文案、`hub.ts` 引用已删文件等；`hub/package.json` 的 test 脚本漏了 `config.test.ts`、`plugins.test.ts`。

## 四、配置分层现状

只有插件是真正三层同构（应用/全局/工作区文件夹）。模型与推理强度只有会话层；语言只有工作区层；限制只有全局层（本轮已按后端分）；界面偏好在 localStorage，中枢看不到。读 JSON 有 7 处实现、容错各异；默认值散在 4 处；原子写已有实现但配置没用。审查给出的统一方案：每层同结构的 `config.json` + 一张设置表（键、所属层、默认、校验、合并规则）+ 一套 `readLayer/resolve/update`（读从不抛、写加锁原子）。

## 五、已经可靠的部分

WAL 多文件提交在 SIGKILL 任意一步后恢复为"全有"，重放幂等，半行能被丢弃；macOS 上 fsync 走 F_FULLFSYNC。输入拿到插入回执后才显示，记录按 messageId 去重；已插入的不会被后续丢弃撤销；非用户停止与抢占按序恢复未读输入；清空、换后端、未恢复、过长续接、超时停止都有分割线；迟到回执按 backendSessionId/turnId 隔离；插件文件夹同构且容错；桌面端重连整体重画不重复。
