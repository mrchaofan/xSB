# 代码评审

登记为 `review/<功能名>`。

## 检查顺序

1. **是否做对了事**：对照 PRD 的验收标准逐条核对，有没有漏做或做多。
2. **正确性**：边界值、空值、错误路径、并发与重入、资源释放。
3. **安全**：外部输入是否校验；有没有注入（SQL、命令、路径）；鉴权是否在服务端；密钥是否硬编码或进了日志。
4. **测试**：新行为有没有测试；测试断言的是行为还是实现细节；失败路径测了没有。
5. **设计**：是否符合技术方案；有没有重复、没用到的代码或过早的抽象。
6. **可读性**：命名、注释是否说明"为什么"。

## 每条意见的格式

- **位置**：`文件:行号`
- **问题**：一句话
- **失败场景**：具体的输入或状态 → 错误的输出或崩溃
- **建议**：怎么改

## 严重度

- **阻断**：会导致错误结果、数据丢失、安全问题，或没有满足"必须有"的需求。必须修。
- **应改**：现在不出错，但很容易出错或难以维护。
- **建议**：可改可不改。

## 结论

写"通过"或"需修改"。有任何阻断项，结论就是"需修改"。没发现问题也要写明你检查了哪些方面，而不是只写"没问题"。
