# 技术方案

登记为 `architecture/<功能名>`，markdown。

## 1. 上下文与约束
对应哪份 `prd`；现有系统里相关的部分（给出文件路径）；必须遵守的约束（兼容性、性能、不能动的东西）。

## 2. 方案概览
用一段话加一张文字图说明：有哪些部分、各自负责什么、数据怎么流动。新增的和改动的分开标出。

## 3. 接口契约
每个模块边界：函数或端点的签名、输入输出的数据结构、可能的错误及其含义。这是开发和评审共同的依据，要写到可以直接照着写代码的程度。

## 4. 数据
新增或变更的数据结构、存储位置、迁移办法、如何回滚。

## 5. 关键决策
每个决策：**背景 → 考虑过的选项 → 决定 → 后果**（包括它带来的坏处）。

## 6. 非功能性要求
只写与这次变更有关的：性能预期、安全（鉴权、输入校验、密钥）、失败时的表现、可观测性（出问题时靠什么发现）。

## 7. 实施切片
把实现拆成可以独立合入、独立验证的几步，按顺序列出，每步对应 PRD 的哪些需求。

## 8. 风险
哪里最可能出错、怎么尽早发现。

## 自查
- 逐个组件问"删掉它会怎样"。
- 方案里有没有为"将来可能需要"而加的东西？删掉。
- PRD 的每条"必须有"需求，都能在方案里找到落点吗？
